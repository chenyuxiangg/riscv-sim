1 为什么要改：那条波形画的不是电平

现场现象：波形面板上只有一条 M16.irq_pulse，纵轴 1～3，常驻在 3，偶发短暂掉到 1。用户据此判断「波形初值是 3」——但 3 不是电平，是中断线号。

第一帧实测
{"t_ps":"2089000000","value":3}   // value = line，不是 level

成因：M-16 在每次 request() 时调 sample_irq_pulse(now_ps, u64::from(line))，M-18 的脉冲通道（pulse=true）把 line 原样当采样值推给 M-19，M-19 按「值变才发边沿」记账 ⇒ 于是「3 一直没有变化」看起来像恒定的电平，而 UART 收到一帧时冒出 line=1 的脉冲。

2 概念空间：三套编号不是一套

这次改动最容易踩的坑是「用一个数字表达两个身份」。本平台的编号分成三套，互相之间只映射、不合并。

4 通道号：内部键，不是身份

M-18 的通道号是 u8，只作内部键使用。对外身份是流 id 与图例标签，前端与断言都不解析这个数字。

5 采样路径：事件驱动，不轮询

单比特通道只在 0↔1 变化时产生边沿（M-19 按值去重）⇒ 重复请求不会刷边沿，长时间挂起也只占一个点。

1设备请求：UART/GPIO 拉高自身 IRQ 电平
2PLIC 网关：set_source_level(src, 1) ⇒ 同步写设备通道 = 1
3宿主裁决：deliverable_source() 有可交付源 ⇒ external 通道 = 1
4M-16 登记：request(line) ⇒ 该线通道 = 1，等 M-17 在量子边界仲裁
5清除：clear() ⇒ 该线通道 = 0；PLIC 源落下不 retract（Renode 口径）

事件写谁写什么 / 注意
M-16 request() 真的登记挂起对应线通道写 1；被掩码丢弃的请求不算
M-16 clear()对应线通道写 0；含 timer 撤线、软中断落、外部无可交付源
