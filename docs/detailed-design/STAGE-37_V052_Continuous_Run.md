# STAGE-37 · v0.52 · 连续运行批（冻结规格）

> **规格号**：STAGE-37　**批次**：第 36 批（v0.52）　**状态**：**冻结**
> **主题**：把「运行」从「点一次走一个窗口」改成「**点一次连续跑**」；「单步」保持「**执行一条指令**」。
> **来源**：用户在 v0.51 批交付后的直接要求 —— 「点击运行后是直接不停运行，只有单步时是执行一条指令」。
> **上一批**：STAGE-36（v0.51 · 波形真图 · echarts）。

---

## §0 本批的边界

- ✅ **要改**：**前端**的「运行」语义 —— 连续运行（跑到断点 / 观察点 / 陷阱 / 暂停为止）。
- ✅ **要改**：前端加「暂停」入口（顶栏），并让「在跑」**看得见**。
- ⛔ **不改**：**契约层**（`SCHEMA_VERSION` / `SIM_STATE_SCHEMA_VERSION` / `PLATFORM_SCHEMA_VERSION` / `PLATFORM_RULES_VERSION` **四个全不动**）⇒ ⇒ **零**新 DTO · **零**新命令 · **零**新事件。
- ⛔ **不改**：**内核 / 宿主**（一行都不改）⇒ ⇒ 「连续」**不是命令的语义**，是**前端循环**的语义。
- ⛔ **不改**：「单步」的语义（**已经是** `StepN { n: 1 }` = 恰好一条指令，实测 +1 ns）⇒ ⇒ **零改动**。
- ⛔ **不改**：脚本口 `window.riscv_kernel.continueRun()` 的语义（**保持「跑一个窗口」**）。
- ⛔ **不改**：需求文档 / 架构文档（本批**没有**新的受控破口 ⇒ ⇒ 两份 HTML **一个字都不改**）。

## §1 为什么要做这一批

### §1.1 用户看到的现象

用户点顶栏「运行」，看到虚拟时间只前进**一小段**就停 ⇒ ⇒ 体感是「**点运行只能单量子时间推进**」⇒ ⇒ 问「不能连续推进？」。

### §1.2 实测事实（每条都对着浏览器加载的**同一个** WASM 产物量过）

| 编号 | 事实 |
| --- | --- |
| F1 | 界面「运行」现在**只发一条** `Continue`：`front/app.js` 的 `handleCommand` 里 `case "continue"` → `commandRouter.dispatchCommand(Command.continueRun())` ⇒ ⇒ **一次点击 = 一个窗口**。 |
| F2 | 契约层 `CommandPayload::Continue` 的语义（`crates/contract/src/protocol.rs`）=「跑到下一个断点 / 观察点 / 陷阱，**或直到本轮指令预算耗尽**」；**量子边界只是抢占点，不是停止条件**。 |
| F3 | 一个窗口 = `DEFAULT_INSTRUCTION_BUDGET`（**10 000 条指令**）⇒ 每条指令 1 ns ⇒ 每量子 1 000 条 = 1 µs ⇒ **一个窗口 = 10 µs = 10 个量子**。实测：虚拟时间 `0 → 10 000 000 ps → 20 000 000 ps → …`（每次 +10 000 000 ps）。 |
| F4 | 跑满预算时内核**主动让出控制权**，并回一个 `Halted { reason: "EndOfExecution" }`（`kernel_host/mod.rs` 的 `on_run`：预算耗尽时 `last_stop` 为空 ⇒ 兜底成 `EndOfExecution`）。 |
| F5 | 契约层 `HaltReason::EndOfExecution` 的**原意**是「Reached end of execution (e.g. `mret` to non-existent PC)」⇒ ⇒ 它**兼表两件事**：「程序真的跑完了」与「只是跑满了一个窗口」⇒ ⇒ 前端**分不清**。 |
| F6 | `Pause` 命令会把 `pause_requested` 标志**留在内核里**（`m17_backend` 的 `pause()` 置位、`take_pause()` 取走即消失）⇒ ⇒ **下一次 `Continue` / `StepN` 会在第一条指令边界就停**。实测：`Pause` 之后紧接着的 `Continue` **一条指令都没跑**（时间 `10 000 000 → 10 000 000`，`reason=UserPause`）；再下一条才正常跑满。 |
| F7 | 宿主是**同步**的（命令在 quiescent point 处理）⇒ ⇒ `Pause` 命令**不可能**停掉一个正在跑的批次 ⇒ ⇒ 它的真实语义是「让**下一个**批次立刻停」。 |
| F8 | 命令的 promise resolve 的是**带同一个 reqId 的第一个事件**（`front/services/m05_commandrouter.js` 的 `handleFrame`）⇒ ⇒ 对 `Continue` 那是 `Tick` ⇒ ⇒ **`Halted` 只能从订阅拿到** ⇒ ⇒ 连续循环**必须**由 `halted` 订阅驱动，**不能**写成 `await` 循环。 |
| F9 | `Halted` 走 `halted` 主题；`front/app.js` 的 `wireDebug` **已经**订阅它并把 `debug.halt` 记进视图状态（STAGE-35 裁决 L）⇒ ⇒ 续跑的落点可以**挂在那一个订阅上**（不新订阅一次 ⇒ 不产生第二个真相）。 |
| F10 | 仓里**已有**「一条一条 `Continue`、循环到命中」的先例：`tools/browser-verify.mjs` 的 osz 段（最多 400 批 + deadline 兜底）⇒ ⇒ 本批是把它**搬进产品 UI**，不是发明新机制。 |
| F11 | 脚本口 `window.riscv_kernel.continueRun()` 被 osz 段用着 ⇒ ⇒ 它必须**保持「跑一个窗口」** ⇒ ⇒ 「连续」与「一个窗口」是**两件事**。 |
| F12 | 调试视图的「继续」按钮是 `data-action="continue"` ⇒ ⇒ 与顶栏「运行」**同一条**命令路径 ⇒ ⇒ 改一处 ⇒ **两处一起变**。 |
| F13 | demo 固件末尾是 `jal x0, 0` **自环**（`0x24`）⇒ ⇒ 连续模式在它上面**永远不会自己停** ⇒ ⇒ 「暂停」必须有**真实出口**，否则真机门禁会被拖死。 |
| F14 | `front/tests/ui-layout.test.mjs` 的 **A-7** 钉了顶栏三个按钮的 action 映射（`run→continue` / `step→step` / `reset→reset`）⇒ ⇒ 加第四个按钮必须**同步扩**那条判据（否则新按钮**零覆盖**）。 |
| F15 | 「复位」= `LoadProject` + 三条内核侧订阅重订 ⇒ ⇒ 连续模式的状态**必须**跟着复位清掉（否则复位后还在跑）。 |
| F16 | 调试视图的「暂停」按钮是 `data-action="pause"` ⇒ ⇒ 它与顶栏新加的「暂停」可以**共用同一个 action** ⇒ ⇒ 一条路径。 |

> ⚠️ **F3 / F6 是本批最重要的两条实测**：F3 推翻了「一个窗口 = 一个量子」的口径（**差 10 倍**）；F6 说明**暂停命令会污染下一次运行** ⇒ ⇒ 「暂停」的实现方式必须重新裁决（裁决 E）。

## §2 裁决

| 编号 | 裁决 |
| --- | --- |
| A | **「运行」= 连续运行**，且「连续」**不是命令的语义**、是**前端循环**的语义 ⇒ ⇒ 契约层零升版、零新 DTO / 命令 / 事件、内核与宿主**零改动**。 |
| B | **「单步」= 恰好一条指令**（`StepN { n: 1 }`）⇒ ⇒ **现状即对**（实测一条指令 = +1 ns）⇒ ⇒ **零改动**；「单步 ×10」同理（10 条）。 |
| C | 连续循环**由 `halted` 订阅驱动**（**不是** `await` 循环）⇒ ⇒ 因为命令的 promise 只 resolve 第一个事件（F8）⇒ ⇒ 落点 = `wireDebug` 里**那一个**订阅（F9）⇒ ⇒ **不新订阅一次**。 |
| D | `EndOfExecution` 的含义**分模式**：`mode === "running"` ⇒ 「让出控制权，**继续**」；`mode === "idle"` ⇒ 「**不续**」⇒ ⇒ 判据必须**分模式**（否则 idle 时也续 ⇒ **空转**）。 |
| E | 界面的「**暂停**」= **停止续发**（前端状态）⇒ ⇒ **不发 `Pause` 命令** ⇒ ⇒ 避开 F6 的残留（否则下一次「运行」会被吃掉一整轮）。**代价**：正在跑的那一个窗口（10 µs 虚拟时间）会跑完才停 —— 用户感知不到。 |
| F | 连续模式的状态住**视图状态** `debug.run = { mode, windows }`（app 层写、视图层只读）⇒ ⇒ 与 `debug.halt`（内核的停下报告）**分开** ⇒ ⇒ 两个不同的真相，两个落点。 |
| G | 顶栏加「**暂停**」按钮（`data-topbar-action="pause"`）+ 一个「连续运行中 / 已跑 N 轮」的**状态指示** ⇒ ⇒ 让「在跑」**看得见**（用户第一眼就知道它在跑）。 |
| H | 「复位」⇒ **退出连续模式**（F15）⇒ ⇒ 否则复位后还在跑。 |
| I | 「运行」**幂等**：已在连续模式时**不重发** ⇒ ⇒ 连点两下不会变成两个并行窗口。 |
| J | 脚本口 `window.riscv_kernel.continueRun()` **保持**「跑一个窗口」（F11）⇒ ⇒ 「连续」是**界面**的语义；两者必须在文档里写清楚。 |
| K | 真机门禁新增 **`runLoop`** 段；**且** `breakpointUi` 段的 B-25 之后**必须**补一次「暂停」收尾（F13 ⇒ 否则 demo 自环永远跑 ⇒ 淹没后续段）。 |
| L | 纯函数落点 = **`front/lib/run-loop.js`** ⇒ ⇒ `nextRunAction` / `runStateAfter` ⇒ ⇒ Node 侧**零 DOM** 可测（与 STAGE-31 的 `compose_memory_map` 同一手法）。 |
| M | 台账登记一条已知边界：「`Pause` 命令在**产品 UI 上没有入口**了」—— 这是**有意**的（F6 / 裁决 E）⇒ ⇒ 契约与前端镜像里它**仍在**（脚本口与契约测试仍覆盖）。 |
| N | **零新版本号**：`SCHEMA_VERSION` 仍 **8** / `SIM_STATE_SCHEMA_VERSION` 仍 **2** / `PLATFORM_SCHEMA_VERSION` 仍 **1** / `PLATFORM_RULES_VERSION` 仍 **3**。 |
| O | **「单步」也会退出连续模式** ⇒ ⇒ 单步 = 走一条**然后停** ⇒ ⇒ 否则「单步」在连续模式下**不可用**（下一轮 `Continue` 立刻把它盖掉）。 |

## §4 已知边界

1. **「暂停」不是「立刻冻结」** —— 正在跑的那一个窗口（10 µs 虚拟时间）会跑完才停（裁决 E / F7）。
2. **`Pause` 命令在产品 UI 上没有入口**（裁决 M）—— 它的语义（让下一批立刻停）会制造残留（F6）。
3. **脚本口 `continueRun()` 是「跑一个窗口」**，界面「运行」才是「连续跑」（裁决 J）—— 两者**不是**一回事。
4. **连续模式在 demo 固件上永远停不下来**（自环，F13）—— 必须靠「暂停」或断点。
5. **连续模式全速跑** ⇒ CPU 占用高（这是「运行」的正常语义，不是缺陷）。

## §6 判别力清单

> ⚠️ **判据必须正向**：断言的是「**被观测的量真的变了**」，不是「某个东西不存在」。

1. **A-2 必须钉住「idle 时不续」** —— 否则把 `nextRunAction` 写成「永远 `continue`」也绿 ⇒ ⇒ **空转通过也是假绿的一种**。
2. **B-35 必须比「> 一个窗口」**，不能比「> 0」—— 后者在「停一次」时也成立 ⇒ ⇒ 零判别力。
3. **B-38 是必要对照**：不点「运行」时时间**不增长** ⇒ ⇒ 否则「时间在增长」可能只是环境噪声。
4. **B-39 是 F6 残留的直接判据**：暂停后再运行，时间**又增长** ⇒ ⇒ 这条一红，F6 就被钉住了。
5. **B-41 钉「stop 语义真的生效」** —— 否则断点后循环继续跑 ⇒ ⇒ demo 自环 ⇒ 真机门禁被拖死。
6. **A-8 钉「幂等」** —— 否则连点两下「运行」会发两条 `Continue` ⇒ ⇒ 两个并行窗口。
7. **A-9 钉「**没有** `Pause` 出去」** —— 只钉「状态变了」的话，把 `pause` 改成「停续发 **且** 发 `Pause`」照样绿 ⇒ ⇒ 残留那条 bug 溜过去。
8. **C-3 钉「单步 = 一条指令」的**逐字**增量**（+1 000 ps）—— 不是「时间变了」。
9. **C-4 钉「单步打断连续模式」** —— 只钉「单步走了」的话，连续模式下一轮 `Continue` 立刻盖掉它 ⇒ ⇒ 单步**不可用**。
10. **B-37 与 B-41 必须自带正向对照**（本批变异自检实测抓到的**判别力缺口**）—— 只判「停」的话，「本来就没在跑」⇒ ⇒ **恒真** ⇒ ⇒ **空转通过也是假绿的一种**。
11. **B-39 的增长量必须 > 一个窗口** —— 只判「> 0」的话，F6 残留那「跑了一轮零指令的窗口」蒙混过关（后面那一轮正常窗口会让它涨起来）。
12. **门禁的「清理」不许依赖「被测的那个按钮」** —— 否则被测物坏了时门禁**卡死**而不是**变红**（实测 900 s 被看门狗砍掉）⇒ ⇒ **清理走独立的路**（本批用「复位」）。

> ⚠️ **空转风险自查**：对每条判据问一句「**如果被观测的对象整个没了，这条判据还会绿吗？**」⇒ 会 ⇒ ⇒ 它就是空的。

## §8 施工期订正

> ⚠️ **本节在施工期填写**：规格冻结后**每改一个字**都要在这里记一条。
> ⚠️ 每条格式：`### 订正 N · 标题`，段内含「规格原文 / 实测 / 已改成」。

### 订正 1 · 「单步 ×10」也要退出连续模式

- **规格原文**：§2 裁决 O 写「「单步」也会退出连续模式」；§5.2 的落点表**只**列了 `handleCommand` 的 `case "step"`。
- **实测**：`case "step10"`（调试视图的「单步 ×10」）走的是**同一个**语义坑 —— 连续模式下点它，下一轮 `Continue` 会立刻把那 10 条盖掉 ⇒ ⇒ 「单步 ×10」在连续模式下**同样不可用** ⇒ ⇒ 裁决 O 覆盖的是「单步」这个**动作**，不是「单步 ×1」这个**按钮**。
- **已改成**：实现里 `case "step"` 与 `case "step10"` **都**先退出连续模式；§5.2 的落点表补上 `case "step10"` 那一行。

### 订正 2 · 顶栏状态位要挂**原始属性**

- **规格原文**：§2 裁决 G 只说「加一个「连续运行中 / 已跑 N 轮」的**状态指示**」；§5.3 说「加一个状态位 `<span data-topbar-run-status>`（内容由 app 层写）」。
- **实测**：判据若只能读中文文案，就得**解析中文** ⇒ ⇒ 换一个措辞就红 ⇒ ⇒ 与「顶栏时间挂 `data-topbar-time-ps`」**不是**同一手法 ⇒ ⇒ 两条同类判据口径不一致 ⇒ ⇒ 对照变异 T-C1（换措辞）就分不清是「措辞变了」还是「判据空了」。
- **已改成**：状态位**额外**挂 `data-topbar-run-mode` 与 `data-topbar-run-windows` 两个**原始属性**；判据读**原始值**；中文措辞改成什么**都不影响**判据 ⇒ ⇒ T-C1 因此是 **0 红**的对照。

### 订正 3 · 续发的「**先写状态、后发命令**」顺序

- **规格原文**：§5.2 说 `wireDebug` 的 `halted` 订阅「按 `nextRunAction` 决定要不要**续发一条 `Continue`**」；F8 说「命令的 promise 只 resolve **第一个**带 reqId 的事件」。
- **实测**：`m05_commandrouter` 的 `handleFrame` 是**先 `resolve` 后 `publish`** ⇒ ⇒ 「`await` 回来」比「订阅回调」**更晚** ⇒ ⇒ 若在 `await` 之后才写「已进入连续模式」，内核让出控制权的那条 `Halted` 会在**还没进连续模式**的时候到达 ⇒ ⇒ 判定落在 `idle` 上 ⇒ ⇒ **续发不成立**（点一次「运行」仍然只走一个窗口）。
- **已改成**：`case "continue"` **先**写 `debug.run = running` **再**发 `Continue`；`halted` 订阅里同理（先 `runStateAfter` 再发）⇒ ⇒ 顺序成为**实现的硬约束**。

### 订正 4 · 续发失败 ⇒ 必须退出连续模式

- **规格原文**：没写。
- **实测**：续发必须**不 `await`**（否则事件处理被内核卡住 ⇒ ⇒ 后面的事件全排队）⇒ ⇒ 失败会变成**未处理的拒绝**⇒ ⇒ 界面会永远显示「在跑」而内核**根本没跑** ⇒ ⇒ 那是界面在骗人。
- **已改成**：续发那个 promise **接 `.catch()`** ⇒ ⇒ 失败时 `setRunState(stopRunState(...))` ⇒ ⇒ 状态位不骗人。

### 订正 5 · 「运行」发不出去 ⇒ 也要退出连续模式

- **规格原文**：没写。
- **实测**：`case "continue"` 里 `dispatchCommand` 会失败（超时 / 传输断了）⇒ ⇒ 那时状态**已经**写成「running」⇒ ⇒ 界面显示「在跑」而内核没跑。
- **已改成**：`case "continue"` 的 `try/catch` 里，catch 分支**先**退出连续模式**再**重抛 ⇒ ⇒ 外层那个 catch 照旧写脚注。

### 订正 6 · 状态指示的同步落点 = `setRunState` 里

- **规格原文**：§5.2 那一行写「`wireTopbarRunbar` | 顶栏「暂停」按钮接线（`handleCommand({ action: "pause" })`）＋ 状态指示同步」。
- **实测**：「状态指示同步」若放在 `wireTopbarRunbar` 里做**订阅**⇒ ⇒ 那就是**第二条**同步路径 ⇒ ⇒ 与「写状态的落点」分处两地 ⇒ ⇒ 少一处可能不同步的地方做不到。
- **已改成**：§5.2 那一行补明「状态指示的同步**在 `setRunState` 里**（写完就同步 ⇒ ⇒ **不订阅**）」；`wireTopbarRunbar` 只在**接线时**同步一次（页面刚打开就该显示「已停止」）。

### 订正 7 · `breakpointUi` 段的「暂停」收尾要**自带判据**

- **规格原文**：§2 裁决 K 说「`breakpointUi` 段的 B-25 之后**必须**补一次「暂停」收尾」。
- **实测**：B-25 撤掉断点后点「继续」⇒ ⇒ 那是**连续运行**⇒ ⇒ demo 固件末尾是自环（`jal x0, 0`）⇒ ⇒ **永远跑下去**⇒ ⇒ 实测那一趟在暂停前跑了 **127 轮** ⇒ ⇒ 只「点了暂停」不算数（点了不等于停了）⇒ ⇒ 收尾本身必须**有判据**。
- **已改成**：真机门禁在 B-25 之后加 **B-25b**（点顶栏「暂停」⇒ ⇒ 断言 `data-topbar-run-mode === "idle"`）⇒ ⇒ 那一条**本身就是**收尾的证据。

### 订正 8 · B-35 的实测口径

- **规格原文**：§3.2 B-35 说「点**一次**「运行」推进的虚拟时间 **> 一个窗口（10 µs）**」。
- **实测**：真机实测 Δ = **2 420 000 000 ps**（= 2.42 ms 虚拟时间 = **242 个窗口**）⇒ ⇒ 远大于一个窗口 ⇒ ⇒ 「点一次跑的是**多轮**」这条口径成立。
- **已改成**：判据保持「> 一个窗口（10 000 000 ps）」；实测值写进 §9 的「实测红集」说明。

### 订正 9 · 幂等判断要**在写状态之前**

- **规格原文**：§3.1 A-8 说「app 层「运行」**幂等**：已在 `running` 时再点 ⇒ **不再发**第二条 `Continue`」。
- **实测**：幂等判断若**在写状态之后**⇒ ⇒ 第二次点击会把 `windows` 归零（`startRunState()` 归零）⇒ ⇒ 用户看得见的「这一趟跑了几轮」被**抹掉** ⇒ ⇒ 幂等就只做到了一半。
- **已改成**：实现里幂等判断**先**做（命中就 `break`）⇒ ⇒ 第二次点击**不写状态** ⇒ ⇒ `windows` 不被归零。

### 订正 10 · 复位清连续模式 ⇒ **轮数一起归零**

- **规格原文**：§2 裁决 H 说「「复位」⇒ **退出连续模式**」。
- **实测**：复位是**新工程**⇒ ⇒ 上一趟跑了几轮与新工程**无关**⇒ ⇒ 只「退出模式」但**保留轮数**的话，界面会显示一个**属于上一个程序**的数字 ⇒ ⇒ 那是**第二个真相**（数字对不上当前程序）。
- **已改成**：复位用 `initialRunState()`（模式与轮数**一起**归零）⇒ ⇒ 而「暂停 / 断点」那种**真停**（裁决 D）**保留**轮数 ⇒ ⇒ 两条路线的语义因此**不一样**，且各自说得清。

### 订正 11 · §9 的变异表要按**实测**回写

- **规格原文**：§9 的「期望红集」列是冻结时的**猜测**。
- **实测**：T2 / T6 / T9 的**实际**红集比期望**多**（超集）⇒ ⇒ 「没预料到的那一条」必须**逐条解释**（判别力通用判据）⇒ ⇒ 冻结时的猜测不能当结论留在规格里。
- **已改成**：§9 改成「**实测**红集」列，并把多出来的那一条**为什么多**写进表里。

### 订正 12 · B-37 与 B-41 必须**自带正向对照**（判别力缺口）

- **规格原文**：§3.2 B-37 写「点「暂停」⇒ 虚拟时间**停止增长**」；B-41 写「断点停下后 ⇒ 虚拟时间**停止增长**」。
- **实测**：这两条**只判「停」** ⇒ ⇒ 若**点之前本来就没在跑**（或者那个按钮**根本不存在**）⇒ ⇒ 「停」**恒真**⇒ ⇒ **空转通过也是假绿的一种**。实测证据：变异 T9（删掉顶栏「暂停」按钮）下 B-37 **没有红** —— 因为时间**本来就在涨**这件事被别处的假红掩盖了；把正向对照补上之后，T9 才让 B-37 **如期变红**。
- **已改成**：B-37 补「点之前时间**在涨**」的前置正向对照（两次采样间隔 700 ms）；B-41 补「停之前**确实在跑**」（用跑过的最大虚拟时间 > 0 证明）。两条都因此**不是空转**。

### 订正 13 · 门禁的**清理不许依赖被测的那个按钮**

- **规格原文**：§2 裁决 K 说「`breakpointUi` 段的 B-25 之后**必须**补一次「暂停」收尾」。
- **实测**：若「收尾」用的正是**被测的那个按钮**（顶栏「暂停」）⇒ ⇒ 一旦它坏了（变异 T9）⇒ ⇒ 连续运行**停不下来**⇒ ⇒ demo 自环把浏览器主线程**灌满**⇒ ⇒ 后面每个 CDP 调用都被拖到几秒 ⇒ ⇒ 整趟门禁**跑不完**（实测跑了 900 s 被看门狗砍掉）⇒ ⇒ **卡死**而不是**变红** ⇒ ⇒ 零判别力。
- **已改成**：`runLoop` 段的**前置清理**改走**顶栏「复位」**（独立于「暂停」；裁决 H：复位 ⇒ 退出连续模式）⇒ ⇒ 清理**永远**能停 ⇒ ⇒ 被测按钮坏了时门禁**变红**而不是卡死。实测：改完之后 T9 那一趟门禁**跑完了**，且 B-37 如期变红。

### 订正 14 · 「暂停」**只**发生在 B-37 里

- **规格原文**：§3.2 把 B-35 与 B-37 并列，没说两者之间的先后与依赖。
- **实测**：若 B-35 那一段**顺手点了暂停**（为了让时间稳定下来读数）⇒ ⇒ 到 B-37 时时间**已经停涨**了 ⇒ ⇒ B-37 的正向对照（「点之前在涨」）**永远不成立** ⇒ ⇒ B-37 **恒红**（本批实测踩到）。
- **已改成**：B-35 只在**运行中**读数（**不**暂停）；「暂停」这个动作**只**出现在 B-37 里 ⇒ ⇒ 两条的依赖关系写死在判据顺序上。
