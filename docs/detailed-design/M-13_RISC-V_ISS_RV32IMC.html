1 功能概述

1.1 模块定位

M-13 为平台自研的 RISC-V 指令集模拟器（ISS），实现 RV32IMC 指令集的解释执行，是仿真内核层（④层）的核心执行单元。模块以“取指、解码、执行”的单指令闭环为基本工作方式：两级解码（opcode 到 funct3/funct7）、表驱动执行、指令与访存钩子、CSR（M 模式为主）、同步异常陷入，中断在量子边界采样后交付。

在平台整体中，M-13 不直接面对前端：所有调试与运行控制均经 ExecutionBackend 抽象（M-17）接入，本模块作为该抽象的自研实现，声明能力等级 L3（L1 基础调试、L2 指令钩子、L3 快照恢复与事件流检查点）。

1.3 MVP 范围与预留

MVP 实现范围：RV32IMC 全量指令（指令全集与实现方式见第 3 章）、M 模式 CSR（mtvec、mstatus、mepc、mcause、mtval、mie、mip 等）、同步异常与中断（详见 5.2）、指令与访存钩子、全状态快照与恢复（配合 M-20/M-23）。

预留项（本模块仅保留演进承接说明，不展开实现）：多核/SMP（FR-18，P2，经 M-17 扩展预留）；S/U 特权模式与虚拟内存（源设计基线未纳入 MVP，后续按需演进）；mtvec 向量模式（MVP 实现直接模式，向量表模式按 FR-06 的向量表配置需求预留）。

2.1.1 复杂结构字段定义

trapInfo 承载当前陷入信息，是异常/中断处理的统一载体（语义见 5.2.4）：

// trapInfo：当前陷入信息（同步异常与中断通用）
struct TrapInfo {
    uint32_t cause;        // 陷入原因：bit31=1 表示中断；低 12 位为异常/中断码（见 5.2）
    uint32_t tval;         // 陷入值：访存异常记访存地址、非法指令记指令编码、其余记 0
    uint32_t pc;           // 触发陷入的指令 PC（同步异常）；中断陷入时为下一条待执行指令 PC
    uint8_t  priv;         // 陷入发生时的特权模式（MVP 恒为 M）
    uint8_t  is_interrupt; // 1=中断陷入，0=同步异常；供调试事件与证据流区分（M-20）
};

decodedCache 缓存两级解码结果，避免热点路径重复解码；含失效规则（store 写内存失效对应 pc、断点地址禁止缓存，评审 13-6）：

// decodedCache：两级解码结果缓存（单条目，按 pc 命中）
struct DecodedCache {
    uint32_t raw;          // 原始指令编码（压缩指令保留 16 位原码，用于 mtval 记录）
    uint16_t compressedRaw;// 压缩指令 16 位原码（非压缩时为 0；评审 13-1）
    uint32_t pc;           // 缓存的取指地址，命中条件
    uint8_t  valid;        // 有效标志；可配置关闭（调试期建议关闭以保真）
    struct {
        uint8_t  opcode;   // inst[6:0]，第一级分派键
        uint8_t  funct3;   // inst[14:12]，第二级分派键
        uint8_t  funct7;   // inst[31:25]（R 型），区分 ADD/SUB、SRL/SRA 等
        uint8_t  rd, rs1, rs2; // 通用寄存器索引（x0 写忽略）
        int32_t  imm;      // 已按指令类型符号扩展的立即数
        uint8_t  cat;      // 指令类别：R/I/S/B/U/J/CSR/SYS/LOAD/STORE/FENCE
        uint8_t  compressed; // 1=压缩指令（展开字段填充、compressed 保留为 1）
    } dec;                 // 解码结果
};
// 失效规则（评审 13-6）：
// 1) 任何 store 完成（自修改代码）→ invalidate 命中该 pc 的缓存条目；
// 2) 断点地址禁止缓存（软件断点写指令字后若缓存命中将执行陈旧解码）；
// 3) decodedCache 可整体关闭（调试期保真）。

hookRegistry 是调试与观测的统一钩子通道，断点（M-08）、trace（M-11）、探针（M-18）、覆盖率共享；回调原型 fn_t(HookKind, const HookEvent*, void*) 与前后钩子语义见下（评审 13-2/B13-3）：

// hookRegistry：钩子注册表（断点 M-08、trace M-11、探针 M-18、覆盖率共享）
// 回调原型（评审 B13-3）：typedef void (*fn_t)(HookKind kind, const HookEvent* ev, void* ctx);
// HookEvent = { pc, raw, compressedRaw, TrapInfo* trap }；ctx 为注册时上下文。
struct HookRegistry {
    fn_t on_fetch;         // 取指成功后触发（含对齐检查结果）；取指异常不触发本钩子，走同步陷入并触发 on_trap（评审 N4）
    fn_t on_instruction_pre;  // 执行前触发：断点命中检测优先于此回调（评审 13-2）
    fn_t on_instruction_post; // 执行成功后、pc_update 前触发（异常路径不触发）
    fn_t on_access;        // 访存钩子：读写事件触发（地址、宽度、值、方向）
    fn_t on_trap;          // trap 钩子：同步异常/中断陷入时触发（trap 事件输出通道，评审 B13-4）
    uint32_t hook_mask;    // 钩子使能掩码：调试态全开时执行性能降级至 0.5-1 MIPS（估算基线）
    uint32_t in_hook;      // 重入保护：钩子回调内不再触发钩子，防止递归
};

perfCounters 为指标与确定性记录提供数据源（mcycle/minstret 读自此处；推进粒度见注释，评审 13-7）：

// perfCounters：性能与行为计数（供 HMS 与指标通道 FR-20 预留）
struct PerfCounters {
    uint64_t inst_retired; // 已退休指令数（minstret 数据源）：每条成功退休指令 +1，异常/中断路径不递增（评审 13-7）
    uint64_t traps;        // 陷入总数（同步异常 + 中断）
    uint64_t trap_streak;  // 连续陷入计数（trap 风暴检测，评审 13-10）
    uint64_t loads;        // 访存读次数
    uint64_t stores;       // 访存写次数
    uint64_t cycles;       // 虚拟周期数（mcycle 数据源，由 M-12 推进，不依赖宿主时钟）
    // 推进规则（评审 13-7/N2）：mcycle = 退休指令数 + 取指周期配额（取指/译码等固定周期由
    // M-12 每量子指令配额折算，默认每条指令折 1 个取指周期）；异常/中断陷入本身不计入退休；
    // 与 Spike 对拍时 mcycle 不比对（仅比对 minstret 与架构状态）。
};

中断交付契约 PendingIntr 与 trap 事件输出通道 TrapEvent：与 M-16/M-12 的交接结构一致，两级仲裁衔接与 mip 视图语义见 5.2.2/5.2.3（评审 13-4/B13-1/B13-4）：

// 中断交付契约（评审 13-4 / B13-1）：与 M-12 v1.1 的 PendingIntr 交接一致
// 两级仲裁衔接：M-16 在量子边界做全局仲裁（特权级比较 + 优先级表）输出单一最高
// 优先级中断；本模块仅检查全局使能（mstatus.MIE）与 cause 编码，不重复仲裁。
struct PendingIntr {
    uint32_t line;   // 中断线号（3=MSI，7=MTI，11=MEI）
    uint32_t cause;  // mcause 编码 = IRQ_BASE(0x80000000) + line
    uint8_t  prio;   // M-16 仲裁输出的优先级（预留；交付时本模块按使能检查）
};
// 接口：bool iss_pending_intr(); void iss_take_intr(const PendingIntr* p);
// mip 视图语义：mip 为 M-16 交付的挂起状态只读视图（level 中断由外设/软件保持请求，
// edge 触发由 M-16 按触发方式管理）；本模块不写 mip。

// trap 事件输出通道（评审 B13-4）：trapInfo → on_trap 钩子（M-18 probe）+ M-12 事件
// 结构（EV_TRAP）+ M-20 事件流记录；消费者：调试器（M-08~M-11）/M-19 波形/M-20 回放。
struct TrapEvent {
    uint64_t    time;    // 虚拟时间（M-12 提供）
    uint64_t    seq;     // 事件序（稳定排序锚点）
    uint32_t    cause;   // 陷入原因（bit31=1 中断）
    uint32_t    tval;    // 陷入值（非法压缩指令记 16 位原码，评审 13-1）
    uint32_t    pc;      // 陷入 PC
    uint8_t     priv;    // 特权模式（MVP=M）
    uint8_t     is_interrupt; // 1=中断，0=同步异常
};

// 快照契约（评审 B13-5）：全状态快照/恢复（L3，配合 M-20/M-23）
struct EngineSnapshot {
    uint32_t version;    // 快照格式版本（不兼容变更时递增）
    uint32_t crc;        // 载荷校验（CRC32，恢复前校验）
    uint32_t regFile[32];// 通用寄存器
    uint32_t csrSet[N];  // CSR 集合（mstatus/mie/mepc/mcause/mtval/mtvec...）
    uint32_t pc;         // 程序计数器
    uint8_t  privMode;   // 特权模式（MVP=M）
    uint64_t instRetired;// 已退休指令数（恢复后续计）
    uint64_t trapStreak; // 连续陷入计数（恢复后续计）
    // 恢复动作（评审 B13-5）：清 decodedCache；重置性能计数基准；
    // 配合 M-12 恢复 progressBase 与虚拟时间（防止恢复后 watchdog 误判）。
};

2.2 CSR 实现清单（M 模式为主）

以 RISC-V 特权架构规范 v20260120 的 M 模式基线实现，MVP 覆盖下表 CSR；未列出 CSR 视为不存在，访问产生非法指令异常（E_ISS-02）。每行一个 CSR，地址与访问属性单独成列，避免合并歧义。

CSR地址访问属性用途与实现要点
misa0x301RO机器 ISA 扩展：声明 RV32IMC（MXL=1，I/M/C 位置位）；只读
mvendorid0xF11RO厂商标识：平台常量
marchid0xF12RO架构标识：平台常量
mimpid0xF13RO实现标识：平台常量
mstatus0x300RW机器状态：实现 MIE、MPIE、MPP 位；写保留位按规范忽略
mie0x304RW中断使能：实现 MSIE、MTIE、MEIE 位（见 5.2.2）
mip0x344RO中断挂起：只读视图，由 M-16 交付的挂起状态更新
mtvec0x305RW陷入向量基址：MODE 为 WARL，仅支持直接模式（MODE=0）；写非 0 MODE 值被钳制为 0（评审 13-9）
mepc0x341RW陷入 PC：异常/中断发生时保存返回地址（语义见 5.2.4）

2.3 数据流说明

指令数据流：fetch 以 pc 从 M-14 取指（32 位/16 位宽度判定见 3.1），decode 产出解码结果，execute 依据解码结果表驱动执行；访存读写经 M-14 分发到 RAM 或外设。trap 数据流：异常/中断写入 trapInfo 并同步更新 mepc、mcause、mtval 与 pc（完整流程见 5.2.4）。

3 指令集实现设计

3.1 取指、译码、执行框架与硬件差异

取指：以 pc 经 M-14 读取指令。先做对齐前置校验再判宽度（评审 13-3）：（a）pc 低 1 位为 1 → 取指未对齐异常（mcause=0，待 M-16 接线：当前实现的 TrapCause 只有一个 MisalignedAccess 变体，暂与访存未对齐共用，接线时须拆分为独立 cause，见 3.6(12)）；（b）pc 低 2 位为 11 → 32 位指令；（c）pc 低 2 位为 00/01/10 → 16 位压缩指令。⚠️ 取指访存宽度恒为 32 位（实现：m13_iss/mod.rs 的 read_mem(pc, WriteSize::Word) / read_fetch(pc, BusWidth::Word)；⚠️ Decoder::fetch_size() 只是该口径的说明性常量，不参与取指路径，v1.7 订正）：低 2 位只用于判宽度，不用于改访存宽度——读回一个 32 位字后，若低 2 位 ≠ 0b11 则取其低 16 位作压缩指令（原码另存于 compressed_raw），否则整字作 32 位指令。理由与硬件一致：真实 RISC-V 核按 32 位粒度取指（I$ 行缓冲），压缩指令只是从 32 位行中选低 16 位；若改成「压缩指令读 2 字节」，每条 32 位指令都得先读半字再读全字，总线访存次数翻倍，且 M-14 上报的访存统计口径随之改变。⚠️ 本条订正了 v1.5 原文「16 位压缩指令，一次读 2 字节」的措辞——该措辞与本文 §3.5 的 C.LW 行「硬件按 32 位取指选低 16 位」自相矛盾。
未对齐检查先于宽度判定与取指访存检查；取指访存未映射时产生取指访存异常（E_BUS-01，mcause=1）。on_fetch 钩子（评审 N4）：取指成功（含对齐检查通过）后触发；发生取指异常（未对齐/取指访存异常）时不触发 on_fetch，异常经同步陷入路径处理并触发 on_trap。⚠️ 压缩扩展使 IALIGN 降为 16（v1.6）：32 位指令允许位于 2 字节对齐地址（pc 低 2 位 = 0b10），因此本模块只检查 pc 低 1 位（必须 2 字节对齐），不检查 4 字节对齐——参考实现同样接受 2 字节对齐的 32 位指令，golden 对拍亦如此。

译码：两级解码。第一级按 opcode 分派指令类，第二级按 funct3/funct7 及立即数类型确定具体指令；表驱动键 = opcode|funct3|funct7 组合（ADD 与 MUL 以 funct7 区分，无 funct7 类别恒取 0，评审 13-5）。立即数按类型拼接并符号扩展（I/S/B/U/J 型规则见下表），B/J 型立即数末位恒为 0。压缩指令按象限与 funct3 展开为等价 32 位编码后填充解码字段，但保留 compressed/compressedRaw 原码（不递归，评审 13-1），mtval 对非法压缩指令记 16 位原码——与真实硬件不同：硬件有独立的压缩解码器（部分核），本模拟器统一经展开层。

// 立即数格式（译码阶段按类型拼接并符号扩展；B/J 型立即数末位恒为 0，无需 ×2 的移位实现）
// I 型：imm[11:0] = inst[31:20]
// S 型：imm[4:0]=inst[11:7]，imm[11:5]=inst[31:25]
// B 型：imm[12]=inst[31]，imm[10:5]=inst[30:25]，imm[4:1]=inst[11:8]，imm[11]=inst[7]
// U 型：imm[31:12] = inst[31:12]，低 12 位补 0
// J 型：imm[20]=inst[31]，imm[10:1]=inst[30:21]，imm[11]=inst[20]，imm[19:12]=inst[19:12]
// 符号扩展统一为：高位置 1 时按 32 位有符号补全（sext）；B/J 型扩展后末位为 0（对齐目标）

执行：查表驱动分派到执行函数（伪代码见 3.2）。公共执行规则：访存经 M-14 并按宽度读写；CSR 经 checkCsrAccess 校验；x0 为目标时寄存器写忽略；指令执行前后触发钩子。

与真实硬件的公共差异（逐指令特有的差异在 3.3/3.4/3.5 各表“与硬件差异点”列说明）：

维度本模拟器（解释执行）真实 RISC-V 硬件核
执行模型顺序、逐指令、指令边界即结果边界流水线（IF/ID/EX/MEM/WB），存在数据冒险、旁路与分支预测
分支总是顺序取指后按结果修正，无惩罚分支预测错误有冲刷惩罚；JALR 为间接跳转预测难点
存储层次无 cache、无 TLB、无 store buffer，访存语义即时有 cache/写缓冲，可见性、一致性与延迟不同（本平台不建模）
时钟虚拟周期由 M-12 推进，与宿主时钟解耦，确定性真实周期，性能与功耗相关
异常/中断指令边界采样与陷入，量子边界仲裁（5.2）流水线内精确异常点，延迟为流水线级
CSR/乘除单周期语义、无惩罚CSR 慢路径、乘除多周期（时延差异不影响架构语义）
x0 寄存器写入直接忽略物理上存在但写被丢弃，语义一致
非对齐访存允许（与 Spike golden 一致），见 3.6实现相关：部分核支持、部分不支持，未定义行为

3.2 表驱动分派伪代码

两级解码 + 表驱动执行的核心示意（本模块实现框架，非最终源码；访存/CSR/钩子的真实调用经 M-14/M-16/M-18 接口）：

// 伪代码：表驱动解码与执行（示意，非真实源码）
// 解码键（评审 13-5）：op 键 = opcode | funct3 | funct7 组合；
// ADD(opcode=0110011, funct3=000, funct7=0000000) 与 MUL(..., funct7=0000001) 以 funct7 区分；
// 无 funct7 的类别（I/S/B/U/J 等）funct7 恒取 0；键未命中 → 非法指令（E_ISS-01）。
typedef struct {
    uint8_t opcode, funct3, funct7;
    uint8_t rd, rs1, rs2;
    int32_t imm;
    uint8_t cat;           // R/I/S/B/U/J/CSR/SYS/LOAD/STORE/FENCE
    uint8_t compressed;    // 1=压缩指令（保留原码，评审 13-1）
    uint16_t compressed_raw;// 压缩指令 16 位原码（非压缩为 0）
    uint8_t len;           // 指令长度：32 位=4 / 压缩=2（v1.7）
    uint8_t illegal;       // 1=保留编码/非法（分派前拒绝，见 3.6(12)，v1.7）
    uint32_t pc;           // 取指地址（v1.7）
    uint32_t raw;          // 原始指令编码（mtval 记录源）
} Dec;

ExecFn exec_table[DECODE_KEY_NUM];   // 表驱动：解码键 → 执行函数（初始化时构建）

Dec decode(uint32_t inst, uint32_t pc) {
    Dec d = {0};
    d.pc = pc;                                 // 取指地址（v1.7）
    if ((inst & 0x3) == 0x3) {                 // 低 2 位=11 → 32 位指令
        d.opcode = inst & 0x7f;
        d.funct3 = (inst >> 12) & 0x7;
        d.funct7 = (inst >> 25) & 0x7f;
        d.rd = (inst >> 7) & 0x1f;
        d.rs1 = (inst >> 15) & 0x1f;
        d.rs2 = (inst >> 20) & 0x1f;
        d.imm = imm_extend(imm_type(d), inst); // 按 I/S/B/U/J 拼接+符号扩展
        d.cat = classify(d);                   // R/I/S/B/U/J/CSR/SYS/LOAD/STORE/FENCE
        d.compressed = 0; d.compressed_raw = 0; d.raw = inst;
        d.len = 4;                              // 32 位指令恒为 4 字节（v1.7）
    } else {                                   // 低 2 位≠11 → 16 位压缩指令
        d.compressed = 1; d.compressed_raw = inst & 0xffff; d.raw = inst & 0xffff;
        d.len = 2;                              // 压缩指令恒为 2 字节（v1.7）
        // ⚠️ v1.7 订正：展开为【字段集】，不是 32 位位模式（见 3.5「展开粒度」）
        Expanded e = c_expand_fields(inst);   // C.xxx → 等价 32 位指令的字段集（表 3.5）
        if (!e.valid) { d.illegal = 1; return d; } // 保留编码 → 非法指令门（见 3.6(12)）
        // 不递归：仅用展开字段填充 opcode/funct3/funct7/rd/rs1/rs2/imm/cat（评审 13-1）
        fill_fields(&d, e);                     // compressed/compressed_raw/raw 保留原码
    }
    return d;
}

int execute(Dec d) {
    // 断点命中检测前置（评审 13-2）：软件断点（M-08）在取指后、执行前判定
    if (breakpoint_hit(d.pc)) { hook(BP_HIT); return BP_HIT; }
    on_instruction_pre(&d);                    // 执行前钩子（含 trace/探针）
    ExecFn f = exec_table[decode_key(d.opcode, d.funct3, d.funct7)];
    if (f == NULL) return E_ISS_01;            // 非法指令→同步陷入（键未命中）
    int rc = f(&d);                            // 执行：访存经 bus_read/write（M-14）、
                                               // CSR 经 check_csr（E_ISS-02）
    if (rc != OK) return rc;                   // E_BUS-01/E_ISS-02 → 同步陷入（不触发 post 钩子）
    on_instruction_post(&d);                   // 执行成功后钩子（异常路径不触发，评审 13-2）
    pc_update(&d);                             // PC 更新：顺序 +4/+2；分支/JAL/JALR/MRET
    return OK;
}

// 执行函数示例（ADD）：exec_table[KEY(0110011, 000, 0000000)]
static int exec_add(Dec* d) {
    if (d->rd != 0) reg_file[d->rd] = reg_file[d->rs1] + reg_file[d->rs2];
    return OK;
}

3.5 RV32C 压缩指令实现清单（26 条）

压缩指令低 2 位不为 11；按象限（Q0/Q1/Q2）与 funct3 解码后展开为等价 32 位指令，复用 3.3/3.4 的执行路径（展开规则见下表“等价 32 位展开”）。C.JR、C.MV、C.EBREAK、C.JALR、C.ADD 共用编码位域，按 rd/rs1/rs2 组合判定，规则遵循非特权规范 C 扩展表 12.4。

⚠️ 展开粒度：字段级展开（v1.6 订正）。本模块把压缩编码展开为等价 32 位指令的字段集（opcode / funct3 / funct7 / rd / rs1 / rs2 / imm），而不是先拼出一个 32 位位模式再拆字段。两者架构语义等价，但字段级展开能把每条立即数规则只写一次、并按其自然宽度携带，避免压缩立即数被迫挤进 32 位立即数字段后再被截断/移位。执行侧仍是同一条路径：c.add 就是 add、c.lw 就是 lw，压缩指令没有第二套执行器（评审 N6）。

立即数规则（全部由参考实现 + 汇编器输出双向取证，v1.6）：

// C.LUI：6 位字段 sext 到 32 位后【截断到 20 位 LUI 字段】再 <<12
//   字段 0b100001 → sext6 = -31 = 0xFFFFFFE1 → 截 20 位 = 0xFFFE1 → <<12 = 0xFFFE1000
//   （参考实现实测 = 0xFFFE1000：专用探针用退出码区分 0xFFFE1000 / 0xFFFFE000）
//   ⚠️ 错法是把 20 位字段取在【高位】：sext6 & 0xFFFFF000 = 0xFFFFE000
//   ⚠️ 但「sext6 <<12」（32 位运算）**不是**错法——左移本身就截到那 20 位
// C.ADDI16SP：位域拼出的【就是字节偏移】（低 4 位恒 0）→ [-512, 496] 的 16 的倍数
//   ⚠️ 不要再 ×16（那会差 16 倍）
// C.J / C.JAL（12 位 CJ 偏移）：位域拼出的【就是带符号字节偏移】（符号在 bit11）
//   → 量程 [-2048, 2046]；⚠️ 不要再 ×2（那会跳到两倍远）
// C.BEQZ / C.BNEZ（9 位 CB 偏移）：位域拼出的【就是带符号字节偏移】（符号在 bit8）
//   → 量程 [-256, 254]；⚠️ 不要再 ×2
// C.ADDI4SPN：nzuimm 由 4 个位域拼出，【非零】才有定义（0 为保留编码）

保留编码 vs HINT 的分类一律以参考实现为准（v1.6）：

  • C.LUI 立即数为 0 → 保留编码（陷阱，不退休）；不是 HINT。
  • C.ADDI4SPN 的 nzuimm = 0、C.ADDI16SP 的 nzimm = 0、C.LWSP 的 rd = x0、C.JR 的 rs1 = x0 → 保留编码（陷阱）。
  • C.MV / C.ADD 的 rd = x0 → 合法空操作（参考实现退休该指令；add x0,… 本就不写任何寄存器），不是保留编码。
  • C.SWSP 的 rs2 = x0 → 真的写 0，不是 HINT。
  • C.SLLI 的 rd = x0 → HINT（写 x0 被丢弃，无架构效果）。
  • RV32 下 C.SRLI / C.SRAI / C.SLLI 的 shamt[5] = 1 → 保留给自定义扩展，陷阱。
  • C.ADDI rd=x0（C.NOP）/ rd≠x0 且 nzimm=0 · C.LI rd=x0 → HINT（退休，但写 x0 被丢弃，无架构效果）。

压缩返回地址调整（评审 N1）：C.JAL/C.JALR 展开后复用 JAL/JALR 同一执行函数，其写 rd 的返回地址按指令长度调整——展开自压缩指令时返回地址取 pc+2（压缩指令下一条地址）而非 pc+4，调整点在执行函数写 rd 处（见下伪代码）；该机制与硬件压缩解码器语义一致。⚠️ 实现取的是 d.len 而不是 d.compressed（v1.6 订正）：write_gpr(state, d.rd, d.pc + d.len)。因为「压缩 ⇒ len=2、32 位 ⇒ len=4」是恒等对应，两种写法架构语义完全等价；取 d.len 的好处是只有一个真相——PC 步进（sequential()）与链接寄存器用的是同一个字段，不会出现「PC 按 2 走、链接寄存器按 4 写」的漂移。

// 压缩返回地址调整（评审 N1）：JAL/JALR 复用同一执行函数，
// 展开自压缩指令时（d.len == 2）返回地址写 pc+2 而非 pc+4
int exec_jal(Dec* d) {                 // JAL 与展开自 C.JAL 共用
    uint32_t ra = d->pc + d->len;    // 调整点：len ∈ {2, 4}
    if (d->rd != 0) reg_file[d->rd] = ra;
    d->npc = d->pc + d->imm;           // 目标地址（符号扩展后已对齐）
    return OK;
}
int exec_jalr(Dec* d) {                // JALR 与展开自 C.JALR 共用
    uint32_t ra = d->pc + d->len;    // 调整点：len ∈ {2, 4}
    if (d->rd != 0) reg_file[d->rd] = ra;
    d->npc = (reg_file[d->rs1] + d->imm) & ~1u;           // 最低位清 0
    return OK;
}

3.6 特殊语义与边界说明

（1）x0 写忽略：所有以 x0 为目标的寄存器写指令不产生副作用，仅保持解码与执行路径一致。

（2）非对齐访存：与 Spike golden 默认行为对齐，允许非对齐访问且不产生异常；非对齐用例纳入对拍。⚠️ 「与 Spike 一致」以参考侧启用 Zicclsm 扩展为前提——Spike 的 riscv/mmu.cc 里 is_misaligned_enabled() 即 extension_enabled(EXT_ZICCLSM)，为假时 throw trap_load_address_misaligned；golden 对拍因此把参考侧 ISA 钉为 rv32imc_zicclsm_zifencei（详见台账 D-42）。

（3）除零与溢出：DIV/DIVU/REM/REMU 按 3.4 表语义执行，属于 guest 语义而非平台错误。

（4）CSR 指令原子性：单线程执行模型下 CSRRW/CSRRS/CSRRC 的读改写天然原子。

（5）FENCE 与 WFI：FENCE 为空操作；WFI 挂起等待中断，唤醒协议与 M-12 配合（见 5.3，评审 13-9）。

（6）decodedCache 失效：任何 store 完成使命中该 pc 的缓存条目失效（自修改代码语义）；断点地址禁止缓存；调试期可整体关闭（评审 13-6）。

（7）mcycle/minstret 粒度：minstret 每成功退休一条指令 +1；mcycle = 退休指令数 + 取指周期配额（M-12 配额折算）；异常/中断陷入路径不递增；与 Spike 对拍仅比对 minstret 与架构状态，mcycle 不比对（评审 13-7/N2）。

（8）trap 风暴检测：连续陷入计数（trapStreak）达到阈值（默认 10⁴ 条全部陷入，估算基线）→ 平台级告警上报 M-12/M-22（mtvec 指向自身等 trap 风暴宿主时间正常、watchdog 无进展检测不触发，须由 trap 率/指令配额检测补充，评审 13-10）。

（9）伪指令与别名：NOP、LI、MV、RET、J、CALL 等汇编伪指令在汇编与反汇编层（M-11）展开，ISS 执行层仅实现机器码。

（10）对拍覆盖：每条指令至少一条正向用例加边界用例（除零、溢出、非对齐、x0、CSR 权限），全部纳入 Spike 差分对拍；新增或变更指令实现须同步扩充对拍用例（评审 13-8：压缩指令 mtval、cache on/off 差分、自修改代码用例见 7.1）。

（11）M 扩展的除零与溢出是「已定义结果」，不是陷阱（v1.6 明确表述）：DIV/DIVU 除零 → 商 = 全 1（0xFFFF_FFFF）；REM/REMU 除零 → 余 = 被除数；DIV/REM 的 MIN ÷ -1 溢出 → 商 = MIN（0x8000_0000）、余 = 0。这是 guest 语义，不产生任何异常，也不计入平台错误码。

（12）C 扩展的保留编码走「同一条非法指令门」（v1.6）：压缩编码展开失败（保留编码 / 属 D、F 扩展的编码点）时，译码器置 Decoded::illegal 并保留 16 位原码（compressed_raw），执行器在分派之前拒绝它 → 报 IllegalInstruction（mcause=2），mtval 记 16 位原码。压缩与 32 位两条路径共用同一个陷阱出口，不另开一条。

（13）压缩指令的 PC 步进与链接寄存器共用同一个字段（v1.6）：两者都取 Decoded::len（压缩 = 2，32 位 = 4）。若两者各写各的常量，就会出现「PC 按 2 走、链接寄存器按 4 写」的漂移——这正是 v0.11 D-16 修的那类缺陷在压缩扩展上的复现。

（14）压缩扩展使 IALIGN 降为 16（v1.6）：32 位指令允许位于 2 字节对齐地址（pc 低 2 位 = 0b10）。本模块只检查 pc 低 1 位（必须 2 字节对齐），不检查 4 字节对齐；参考实现同样接受 2 字节对齐的 32 位指令，golden 对拍亦如此（语料 rv32uc/rvc 即含此类用例）。

（15）「保留编码」与「HINT」的分类直接决定 golden 对拍结果（v1.6）：把保留编码当成 HINT（照常退休）或反之，都会在对拍时变成「一侧陷阱、一侧退休」的判决不一致，且失败用例号也对不上。分类口径以参考实现为准，逐条见 §3.5。

5.2.3 中断仲裁与优先级

两级仲裁衔接（评审 13-4/B13-1）：M-16 在每个量子边界采样外设/定时器/软件中断源，做全局仲裁（特权级比较 + 优先级表）后输出单一最高优先级中断 PendingIntr；本模块不重复仲裁，仅做全局使能检查（mstatus.MIE=1）并按 cause 编码陷入。M 模式范围内优先级：MEI（11）> MSI（3）> MTI（7）（由 M-16 仲裁表执行）。未使能或全局屏蔽（MIE=0）的中断保持挂起不丢失，待使能后在指令边界交付。

5.2.4 陷入与返回完整流程

同步陷入（异常与中断共用路径，见 5.2.1/5.2.3 的触发条件）：

（1）mepc ← 陷入点：同步异常为触发指令地址（ECALL/EBREAK 记自身地址）；中断为下一条待执行指令地址。

（2）mcause ← 陷入原因：异常记异常码；中断记中断码且 bit31 置 1（如 0x8000000B）。

（3）mtval ← 陷入值：访存异常记地址、非法指令记编码（非法压缩指令记 16 位原码，评审 13-1）；中断时保持原值（规范允许不清零）。

（4）mstatus 状态保存：MPIE ← MIE；MIE ← 0（屏蔽中断防重入）；MPP ← M。

（5）pc ← mtvec：MODE 为 WARL 仅支持直接模式（MODE=0，写非 0 被钳制，评审 13-9）；向量模式预留。

（6）trap 事件上链：写 trapInfo 并构造 TrapEvent{time, seq, cause, tval, pc, priv, is_interrupt}，经 on_trap 钩子（M-18 probe）与 M-12 事件引擎/M-20 事件流输出；消费者：调试器（M-08~M-11）/M-19 波形/M-20 回放（评审 B13-4）。

返回（MRET）：mstatus.MIE ← MPIE、MPIE ← 1；pc ← mepc；恢复执行。重复陷入语义（评审 13-9）：中断交付后 mip 挂起位由 M-16 按触发方式管理（level 中断由外设/软件保持请求——外设未清除则 MRET 后若仍使能会立即再次陷入，这是规范语义；edge 触发由 M-16 交付时清除），本模块不额外清位、不阻止合法重入。MVP 仅 M 模式，MPP 不参与特权切换。

5.2.5 边界情况与硬件差异

（1）嵌套中断：硬件在陷入时自动清 MIE 屏蔽后续中断；MVP 为单层处理，固件可在 handler 内显式重新使能以实现嵌套。

（2）同时发生：同一指令边界同步异常优先于中断；多中断由 M-16 按优先级仲裁取最高者交付（5.2.3）。

（3）中断风暴抑制：按 mie 使能掩码与 M-16 优先级仲裁抑制，未使能中断保持挂起不丢；guest 失控判定（指令预算 watchdog）归 M-12，与 guest trap 严格区分。

（4）trap 风暴（评审 13-10）：trapStreak 连续陷入计数达阈值（默认 10⁴ 条，估算基线）→ 平台级告警上报 M-12/M-22（如 mtvec 指向自身，宿主时间正常、watchdog 无进展检测不触发，须由本模块 trap 率检测补充）。

（5）与硬件差异：真实核在流水线内取精确中断点（如 load 完成/异常指令），模拟器在指令边界与量子边界采样，对可观测行为更保守、确定性强；真实硬件有 MPP/MPRV/虚存等机制，MVP 仅 M 模式从简。

5.3 量子混合调度

M-12 通过 runUntil/step 驱动本模块：连续运行模式下按量子批量执行指令（每量子指令配额），到达事件边界或检查点暂停；控制注入（暂停、断点、单步）只在安全检查点生效。本模块不自行轮询宿主时钟，虚拟时间完全由 M-12 推进（确定性约束）。

WFI 唤醒协议（评审 13-9）：WFI 执行后置 wfi_pending，本模块停止取指；M-12 在量子边界检查待交付中断（M-16 仲裁结果），存在使能中断（mstatus.MIE=1 且 cause 有效）时唤醒本模块进入陷入路径；无使能中断时 M-12 在空闲区间批量推进虚拟时间（不空转），不误判 guest 失控。

5.3.1 虚拟时间模型 sim_now

量子混合调度的根基是虚拟时间单一时间基准：全局时间戳 sim_now 统一驱动 ISS、总线与外设，事件驱动与时间驱动两条推进路径在同一时间域内结算。

（1）时间域隔离定义：虚拟时间（仿真域）——sim_now 为全局时间戳，单位 ns，纯内存变量；无硬件晶振、不读取宿主机系统时钟。宿主机墙上时间（host wall clock）仅用于 Worker 看门狗（5.3.5-3）与前端 UI 渲染节流，不参与仿真时序计算。

（2）sim_now 的三类更新入口（核心）：入口 1——ISS 执行指令，逐条累加指令虚拟时延（细粒度步进，见 5.3.2）；入口 2——事件调度，直接跳跃至事件时间戳（批量跳时间、消除空转，见 5.3.4）；入口 3——总线事务处理，在仲裁/传输阶段增量推进 sim_now（见 5.3.3）。

（3）量子边界约束：量子为虚拟时间检查卡点（默认 1000 ns，估算基线、可配置）；允许指令执行轻微越界（指令必须完整执行，见 5.3.7-4），中断最大延迟等于量子大小（见 5.3.7-3）。

5.3.2 ISS 指令时序模型与时延表

每条指令执行时延由静态时延表（基础时延 T_base）与访存总线时延（T_bus_total，见 5.3.3）叠加维护，作为 sim_now 细粒度步进的来源。

（1）指令时延表（Instruction Timing Table）：静态配置表，仿真启动加载；按 opcode+funct 索引获取指令基础时延 T_base。模型说明：事务抽象模型，不完整模拟 CPU 流水线冒险、旁路、stall（默认关闭流水线精细建模，可配置开启）；指令视为原子执行单元，不可在指令执行中途打断。

（2）普通运算指令时序：仅叠加 T_base，直接加到 sim_now（T_instr = T_base，表 2 示例基线）。

（3）访存指令时序模型：总耗时 T_instr_mem = T_base + T_bus_total；流程：ISS 译码 → 累加基础时延 → 发起总线事务 → 总线模型计算并叠加总线事务全部时延（T_bus_total 定义见 5.3.3）。

（4）可选高级能力：Cache 建模（开关控制，默认关闭；开启后额外增加 cache miss 时延，不影响架构语义与 golden 对拍）。

5.3.3 事务级总线模型（TLM）与总线延时计算

总线模型是访存时序的来源：本模块的 load/store 与取指均经 M-14 分发，M-14 内实现事务级总线模型，本小节定义其时序语义（本模块只按契约发起与结算时延）。

（1）总线模型定位：简化 AHB 事务级模型（TLM），非周期精确 RTL；一次读/写打包为一条总线事务，不逐周期仿真握手信号；无独立时钟源，全部时序依赖全局 sim_now。

（2）总线内部状态变量：bus_free_time——基于 sim_now 的时间戳，标记总线释放时刻，多 Master 仲裁核心状态；地址映射路由表——地址区间映射至从设备实例；总线静态配置——路由时延 T_route。

（3）总线事务延时分解公式：T_bus_total = T_arb + T_route + T_slave。其中 T_arb 为仲裁等待延时，动态计算 T_arb = max(0, bus_free_time − sim_now)；T_route 为路由译码固定开销（静态配置参数）；T_slave 为从设备访问时延，由从设备 access() 回调返回（RAM/Flash/GPIO/UART 各自独立配置，支持动态状态相关时延）。

（4）一次总线事务完整执行流程（四步，对应图 3）：① ISS 发起 load/store 请求 {addr, dir, width}；② 仲裁等待：计算 T_arb（多 Master 串行，见（5））；③ 路由 + 从设备访问：查路由表定位从设备，调用 access()，累加 T_route + T_slave；④ 总线状态更新：bus_free_time = sim_now + T_bus_total，返回数据或错误（E_BUS-01 访存异常）。

（5）多 Master 并发处理规则：CPU、DMA 等主设备串行仲裁；同一时刻仅一条总线事务在传输，后续发起者在 bus_free_time 之后才获准（T_arb 自然体现等待）。

（6）总线状态更新语义：事务结束更新 bus_free_time 为下一次仲裁基准；总线自身无独立时钟，释放时刻完全由事务时延决定。

5.3.4 外设事件与定时器时序建模

外设（M-15）不持有独立时钟，事件全部基于全局 sim_now 产生并进入调度事件堆，与 ISS/总线共享同一时间域。

（1）外设统一时序规则：所有片上外设共享全局 sim_now 作为唯一时间基准；多时钟域仅修改 tick 周期参数（预分频系数），不存在独立振荡器。

（2）MTIME/SysTick 定时器建模：定时器维护 timer_next_trigger 时间戳，基于当前 sim_now 与预分频/计数周期计算（timer_next_trigger = sim_now + prescaler × period）；将 timer_next_trigger 事件推入全局最小堆事件队列；调度器推进 sim_now 到达触发时间，弹出事件，执行外设逻辑、产生中断请求标记（对应 2.2 新增 mtime/mtimecmp CSR，见 5.2.2 MTIE）。

（3）中断采样规则：外设仅标记中断请求（mip 挂起视图由 M-16 交付状态更新），中断统一在量子边界采样仲裁，不在事件发生时刻立即响应（衔接 5.2.2/5.2.3）。

5.3.5 全局调度器宿主机执行模型

调度器是运行于 Worker 线程内的主循环代码（非独立操作系统进程），仿真内核整体驻留 Worker，与前端主线程隔离。

（1）调度器载体与线程架构：主线程（UI、控制命令、前端交互）+ Worker 线程（仿真内核：调度器、ISS、总线、外设实例、独立 sim_now、独立事件堆），双线程经结构化消息交互（控制注入/状态上报）；多 SoC 并行：多 Worker，每个 Worker 拥有独立仿真域，互不干扰（架构见图 4）。

5.3.6 调度核心算法伪代码

以下为参考实现（Python 风格伪代码，便于评审理解逻辑，不作为最终工程代码），整合量子循环、事件堆、sim_now 推进、ISS 执行、总线事务调用与量子边界中断采样：

# 调度主循环（参考实现）：量子批量 + 事件堆 + sim_now 推进 + 边界中断采样
sim_now = 0                     # 虚拟时间（ns），仿真域唯一时间基准（5.3.1）
bus_free_time = 0               # 总线释放时间戳（5.3.3）
event_heap = MinHeap()          # 全局最小堆：未来事件按 (t, seq) 稳定排序
QUANTUM = 1000                  # 量子大小（ns，估算基线，可配置；5.3.1-3）
wfi_pending = False             # WFI 停取指标志（引言协议）

def scheduler_run():
    while not stop_requested:
        quantum_end = sim_now + QUANTUM
        # ① 事件驱动优先：批量跳跃至最近事件时间戳，消除空转（5.3.1 入口2）
        while event_heap and event_heap.top().t <= quantum_end:
            ev = event_heap.pop()
            sim_now = max(sim_now, ev.t)     # 直接跳跃至事件时间戳
            ev.dispatch()                    # 外设逻辑：执行/置中断请求标记（5.3.4）
        # ② ISS 细粒度步进：量子内逐条执行指令（5.3.1 入口1）
        while sim_now < quantum_end and not wfi_pending:
            inst = fetch(pc)                 # 取指经 M-14：总线事务，推进 sim_now/bus_free_time
            sim_now += inst.T_base           # 累加指令基础时延（5.3.2）
            if inst.is_mem_access():
                sim_now += bus_transaction(inst)  # 总线事务：T_arb+T_route+T_slave（5.3.3 入口3）
            execute(inst)                    # 表驱动执行；允许 sim_now 轻微越界（5.3.7-4）
            if inst_retired >= inst_budget:  # 指令配额保护（可选，M-12 指令预算折算）
                break
        # ③ 量子边界：中断采样与交付（5.3.4-3 / 5.2.2/5.2.3）
        if event_heap and event_heap.top().t <= sim_now:
            continue                         # 下一事件恰在边界内 → 回①处理（不空转）
        irq = m16_arbitrate(sim_now)         # M-16 量子边界全局仲裁 → PendingIntr
        if irq and mstatus.MIE:
            take_interrupt(irq)              # 陷入路径（5.2.4）；下量子执行 handler

5.3.7 约束与边界说明

（1）确定性约束：时延表、总线配置、量子大小均为固定静态参数，禁止引入宿主机时间随机量（与 1.2/2.4 确定性约束衔接）；同一种子 + 同一输入序列 → sim_now 推进序列唯一。

（2）模型取舍：事务级抽象（TLM），不模拟总线信号毛刺、流水线冒险/旁路/stall；可选高级模式（流水线精细建模、Cache 建模）默认关闭，开启不影响架构语义与 golden 对拍。

（3）中断延迟上限：中断最大延迟等于量子配置值（量子为采样卡点，外设中断请求在下一量子边界交付，见 5.3.1-3/5.3.4-3）。

（4）时间越界规则：指令必须完整执行（原子单元，5.3.2-1），允许 sim_now 轻微越过量子边界；量子为检查卡点而非硬截止，不截断执行中的指令。

5.3.8 参考范式说明

本方案参考 Renode 量子调度（虚拟时间驱动事件循环）、QEMU icount 指令时序模型（指令计数折算虚拟时钟）、Spike 指令译码与异常语义（golden 对拍基线）；平台改造点：按虚拟时间量子切片（sim_now 单调推进 + 事件堆批量跳跃），而非指令计数切片（QEMU icount 式）。

9.4 会话状态导出 / 载入接口（本轮落点 · 台账 D-41）

⚠️ M-13 没有关联状态——Iss 是纯解释器：它不持有 CPU 的架构状态（gpr / pc / csrs），那些状态在契约的 SimState 里，由 M-12 / M-17 承载。因此 M-13 侧没有独立的导出 / 载入接口（既无 exportState，也无 loadState）——这不是遗漏，而是 M-13 没有可导出的状态。会话载荷里 CPU 架构状态的唯一落点是 m12Engine.state（M-12/M-17 段）；m13State 段只承载内存页（RAM 内容）——同一份寄存器存两处就是两个真相（见 M-20/M-23 §2.1.1 裁决 B）。

接口方向契约（输入 → 输出；错误码/约束）
（无会话状态接口）—M-13 不提供状态导出 / 载入接口——纯解释器，不持有 CPU 架构状态
取指 / 访存提供（driving）会话恢复时经 M-14 取指 / 访存读回已回灌的内存页（段 2）——M-13 不复制内存内容
m12Engine.state由 M-17 承载CPU 架构状态（gpr / pc / csrs）的唯一落点；恢复由 M-17 restore_full 覆盖

恢复顺序（不可换）：① M-14 load_map（映射）→ ② M-14 load_pages（内存页）→ ③ M-15 load_state（外设状态）→ ④ M-16 load_state（IRQ 行）→ ⑤ M-17 restore_full（引擎段）。⚠️ 校验先于应用：载荷必须先整体校验通过，再按上述顺序逐段回灌——半个应用完的快照比被拒绝的快照更糟。
