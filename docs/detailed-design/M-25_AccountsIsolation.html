1 功能概述

1.1 模块定位

M-25 是 riscv_sim 的身份与隔离层：它把「谁在用这台仿真器」变成可判定的事实，并保证一个账号看不到、也碰不到另一个账号的会话、console 与镜像。它回答三个问题：这个请求是谁（鉴权）、这个会话属于谁（归属）、这个账号还能再开几个（配额）。

它不是内核模块。M-13 仍然解释指令，M-12 仍然持有虚拟时钟，M-17 仍然是执行后端 —— 内核完全不知道「账号」这个概念存在。M-25 只做四件事：凭据解析（cookie / Bearer / 兼容头）、归属判定（SessionHandle.owner）、资源分根（镜像目录按账号切）、配额（全局 + 单账号）。

三条设计红线：

  • 不改契约：SCHEMA_VERSION 停在 21。登录是 REST、令牌是 HTTP 头 —— 会话归属不进 Message，也不进 boot 回体。
  • 单点判定：鉴权只在 require_auth 判一次；handler 只使用已判定的 Identity，不重复判、不各自造规则。
  • 默认兼容：没有账号库时一切照旧（单令牌 SIM_TOKEN 行为不变），上线不要求一次性搬完所有东西。

1.2 需求承接

需求来自「两个域名对外公开」的拍板口径：rsim.lczyzs.xyz 给浏览器、rsimmcp.lczyzs.xyz 给 MCP，账号体系为「一用户一账号、一账号多 token、token 用于 MCP」。五条要点全部有落点。

2 数据描述

2.1 账号库

账号库是唯一的身份来源，一个 JSON 文件，启动时读一次进内存，运行期只读不写（增删账号走 tools/accounts.py）。结构固定为三层：文件 → 账号 → 令牌。

表 3 · 账号库字段（accounts.json）

层级字段类型语义与约束
文件versionu32必须为 1；不等于 1 ⇒ Accounts::load 回 Err，启动失败（不猜别的版本）
accountsVec<AccountRecord>账号全表；文件缺席 ⇒ Ok(None) ⇒ 兼容模式
AccountRecordidString（acc-XXXXXX）随机 6 位十六进制；会话 owner / 镜像目录名都用它，改名不动它
nameString登录名；比对时转小写（Alice 与 alice 是同一个账号）
roleString（user / ops）本批只做标记与回显，不做权限分级；P1 才按 role 放行代管
passwordStringpbkdf2_sha256$<iter>$<salt_b64url>$<hash_b64url>；默认 200 000 轮
tokensVec<TokenRecord>一账号多令牌；可空（只有 cookie 登录、不接 MCP 的账号允许没有令牌）
createdu64（秒）建账号时间；仅用于列举与审计展示，不参与判定
TokenRecordidString（tok-N）令牌 id；/api/whoami 回 token_id，用于对着 CLI 吊销
hintString（前 4 字符）给人看的前缀，便于「这把钥匙是哪把」；不足以登入（校验只看 hash）
hashString（64 hex）sha256(token) 小写十六进制；比对走常数时间，比较的是 hex 串
created / revokedu64 / boolrevoked=true 即不再认；保留记录而不是删行，便于事后追「谁吊销过什么」
约束密码与令牌都只存不可逆摘要：密码是 pbkdf2 派生，令牌是 sha256。明文令牌只在签发那一刻打印一次，文件权限固定 0600，tools/accounts.py list 也不回显明文 —— 这三条是「账号库被读走也不等于被登入」的全部本钱。

文件首行的示例（脱敏）如下。注意 hint 与 hash 的关系：前者是名字，后者是判据。

      "id": "acc-c9d46d",
      "name": "alice",
      "role": "user",
      "password": "pbkdf2_sha256$200000$Yk9x…$3f2a…",
      "tokens": [
        { "id": "tok-1", "hint": "UW78", "hash": "6f1c…（sha256 全 64 hex）",

2.2 身份与渠道

Identity 是请求级结构：一次请求解析一次，活在 handler 的 Extension 里，不进会话、不进契约。它把四种凭据渠道收敛成同一组字段 —— 这是「两条入口一个终点」的实现面。

表 4 · Identity 字段与凭据渠道

项类型来源渠道语义与约束
accountString全部渠道归属判据。账号模式下来自 AccountRecord.id；SIM_TOKEN 下固定为 ops；兼容模式固定为 legacy
nameString全部渠道展示名；与 account 分开，因为 id 不可读、name 可读
roleString全部渠道user / ops；本批只回显
token_idOption<String>Bearer / X-Auth-Token / ?token=命中的 TokenRecord.id；cookie 渠道为 null（cookie 不代表某一把令牌）
channelString系统判定cookie / bearer / header / query / compat；只用于回显与排障，不参与授权
——cookie sim_auth优先级 1；HttpOnly; SameSite=Lax; Max-Age=43200；Secure 只在 X-Forwarded-Proto: https 时给
——Authorization: Bearer优先级 2；MCP 与 CI 的主路；后端只认这一个标准头，MCP 内部另有 x-mcp-token 的对内兼容
——X-Auth-Token优先级 3；v0.1.9 之前的旧客户端的兼容头，等价于 Bearer
——?token=（仅 /events/ws）优先级 4；唯一允许出现在 URL 的令牌，因为浏览器 WebSocket 不能带自定义头
——SIM_TOKEN（进程环境）兼容兜底：账号模式下映射 Identity::ops()；看不见任何账号会话（owner 不匹配），只能建自己的
为什么叫 ops 而不是「管理员」：它没有「看别人会话」的权力，只保留「进程级应急」的能力 —— 上线当天忘记建账号时不至于把自己锁在门外，同时不给运维一个默认的越权通道。真正的代管能力（role=admin 看他人会话）留给 P1，并要求显式开关。

2.3 会话归属

归属是一个字段，不是一张映射表：SessionHandle.owner 在 create_for 时写入，之后不可变（会话不可转让）。所有「这个会话归谁」的判定都从它出发。

表 5 · 归属相关结构与判定

对象字段/方法类型语义与约束
SessionHandleownerString创建时的 Identity.account；不可变；随会话一起被回收
SessionRegistrymax_per_accountusize默认 usize::MAX（未配置即不限额）；由 set_max_per_account 在启动时设一次
create_for(board, source, owner)→ Result<SessionId>全局与单账号两条配额在同一把锁里判：先全局（E_SESS-05 detail 为空）再账号（detail account_quota）
list_for(owner)→ (Vec<Info>, max, used)只列 owner 匹配的会话；max 报的是该账号上限（不是全局），避免把全局余量泄露给别人
owner_of(id)→ Option<String>会话不存在 ⇒ None ⇒ 调用方回 404；不做「存在但无权」的第二条错误分支
reaperTTL 扫表—按 session_ttl 回收；与 owner 无关 —— 空闲会话被回收不因账号不同而区别对待
约束「越权与不存在同回 404」是安全要求：若越权回 403、不存在回 404，攻击者可以用状态码差异探测会话 id 是否有效。因此 owner_of 与 get 的失败在 HTTP 层必须折叠成同一个响应，detail 也不得泄漏另一个账号的名字。

3 体系结构

3.1 组件与边界

M-25 由五个零件组成，全部在 crates/server 内：账号库、凭据解析中间件、归属与配额（在 SessionRegistry 上）、镜像分根（一个纯函数）、页面门（在 front_or_unknown 里）。没有新 crate、没有新进程。

表 8 · 组件与职责边界

组件文件职责不负责
账号库 Accountssrc/account.rs加载/校验账号库；令牌与密码校验；cookie 会话表（签发/解析/登出）不知道会话、不知道 HTTP、不写文件
鉴权中间件 require_authsrc/api.rs按固定次序取凭据 → 解析 Identity → 归属校验 → 注入 Extension不做配额（配额在 create 里）、不做分根
归属与配额src/session.rsowner 字段、create_for / list_for / owner_of、两条配额不判凭据、不碰磁盘
镜像分根 image_root_forsrc/api.rs按 identity 选根并按需建目录不做路径规范化（那是 whitelist_path 的事）
页面门src/api.rs（front_or_unknown）静态资源与 /：账号模式 + Accept: text/html + 无 cookie ⇒ 302；?token= 有效 ⇒ 换 cookie 后 302不拦 /api/* 与 /login.html 本身（否则死循环）
运维 CLItools/accounts.py离线 init/add-account/add-token/revoke-token/list；与 Rust 同一文件格式、同一 PBKDF2 参数不在运行期调用服务端；不存明文
MCP 租户解析mcp/server.py_resolve_client(token)：whoami → account 作租户键；会话记录钉住令牌不做鉴权判定（服务端才是判据）

3.2 请求处理路径

一个请求的路径是固定的一条直线，没有分支式中间件链：解析凭据 → 归属校验（若有会话 id）→ handler。三个 handler 之外没有第二处鉴权，这也是「不重复造规则」的结构保证。

表 9 · 各端点的判定点

3.3 与既有模块的关系

关系可以一句话概括：M-25 只改「谁能进」，不改「进去之后发生什么」。

  • M-24（HTTP 宿主）：M-25 是它的一个中间件 + 一组端点 + 一个分根函数；M-24 的路由表、错误映射、线程模型都不动。
  • M-04（会话管理，浏览器侧）：服务端侧的对应物是 SessionRegistry；M-25 只给它加 owner 与两条配额。
  • M-07（传输适配）：WS 的 ?token= 例外仍按原样保留，M-25 只是同意在解析阶段接受它。
  • M-18（Probe）/ M-19（波形）/ M-22（HMS）：与账号无关，全部沿用。
  • 内核（M-12/M-13/M-17）：零改动。内核不认识账号，这正是本设计能「不动契约」的根因。

4 详细设计

4.1 凭据解析

解析次序固定且不可配置（cookie → Bearer → X-Auth-Token → 仅 WS 的 ?token= → 兼容 SIM_TOKEN）。固定次序的意义是：同一个请求带两种凭据时，结果可预测，不会因部署差异而变。

// crates/server/src/api.rs（示意，非逐字代码）
fn resolve_identity(state, headers, uri) -> Option<Identity> {
    // 1. cookie：账号模式的名字牌（HttpOnly，JS 读不到）
    if let Some(cookie) = cookie_from_header(headers) { if let Some(id) = accounts.resolve_cookie(&cookie) { return Some(id); } }
    // 2. Bearer / 3. X-Auth-Token：MCP 与 CI 的主路
    for token in bearer_tokens(headers) {
        if let Some(id) = accounts.authenticate_token(&token) { return Some(id); }
        if token_accepted(&state.token, &token) { return Some(Identity::ops()); }   // 兼容兜底
    }
    // 4. ?token=：只认 /events/ws（浏览器 WS 不能带自定义头）
    if wants_ws(uri) { if let Some(t) = query_token(uri) { … } }
    None
}
约束常数时间比较：令牌比对用 constant_time_eq 逐字节等时，避免「按前缀长度提前返回」把令牌泄漏成计时侧信道。同理，登录失败时错用户与错密码同为 None，不区分「没这个人」与「密码不对」。

4.2 口令与 cookie

密码用 PBKDF2-HMAC-SHA256 自实现（不引第三方 crate 之外的依赖），参数写进字符串本身，便于以后调迭代数而不破坏旧记录。

口令校验按记录里的 iter / salt 重算后等时比对登录与 CLIRFC 向量（c=1 / c=2）在单测里钉住，防止自实现跑偏

cookie 属性Path=/; HttpOnly; SameSite=Lax; Max-Age=43200响应头SameSite=Lax 让「从外部链接点进来」也能带上 cookie，同时挡住跨站 POST
Secure仅当 X-Forwarded-Proto: https响应头反代后面才加 https，本地 http 开发若硬加 Secure 会导致 cookie 存不下
会话 TTL12 h，滑动续期session.rs（cookie 表）每次解析成功即续期；过期即 None（等价于未登录）
登出删 cookie 表项 + Set-Cookie Max-Age=0POST /api/logout幂等：重复登出仍 204

4.3 会话归属与配额

两件事在同一把锁里做，是为了避免「先判全局再判账号」之间被别的线程插队：

  • ① 全局活会话数 ≥ max_sessions ⇒ 429（detail 不提账号）；
  • ② 该账号活会话数 ≥ max_sessions_per_account ⇒ 429（detail account_quota）；
  • ③ 两条都过 ⇒ 分配 id、写 owner、登记，返回 201。

4.4 镜像分根

一个纯函数 + 一次 create_dir_all：

pub(crate) fn image_root_for(state: &AppState, identity: &Identity) -> Option<PathBuf> {
    let root = state.image_root.as_ref()?;
    if state.accounts.is_none() { return Some(root.clone()); }        // 兼容：原根不动
    let dir = root.join(account_dir_name(&identity.account));
    std::fs::create_dir_all(&dir).ok()?;                              // 惰性创建
    Some(dir)
}

fn account_dir_name(account: &str) -> String {
    account.chars().map(|c| if c.is_ascii_alphanumeric() || c == '_' || c == '-' { c } else { '_' }).collect()
}
分根之后白名单逻辑不变：upload::whitelist_path(root, path) 仍做 canonicalize + starts_with(root)。两层的分工是：M-25 保证「根是这个人该看的根」，白名单保证「路径出不了这个根」。任一层单独都不够。

4.7 MCP 侧透传

MCP 从「服务凭据即全权」改成「谁的令牌就用谁的身份」。三个改动点：

  • ① 令牌不再强制：SIM_MCP_TOKEN 只在「设了且等于 SIM_TOKEN」时报错退出（防误配成同一把）；
  • ② 每次请求把客户端令牌放进线程本地 _TOKEN_CTX，_http(..., token=None) 默认取它（回退 SIM_TOKEN）；
  • ③ _resolve_client(token)：先认 SIM_MCP_TOKEN（服务凭据 ⇒ c-<hash8>），否则查缓存 / 调 GET /api/whoami，账号模式取 account 作租户键。

表 14 · MCP 租户键与回收

情形租户键会话表回收行为

5 关键流程

5.1 浏览器登录

  • ① 打开 /：账号模式 + HTML + 无 cookie ⇒ 302 /login.html；
  • ② 登录页先探 /api/auth/mode：accounts:false ⇒ 直接 replace("/")（兼容模式无需登录）；
  • ③ 提交 POST /api/login：成功 200 + Set-Cookie + {account,name,role}；失败 401 + detail invalid credentials，页面显示「账号或密码不对」；
  • ④ 回 /：页面同源探测 /api/version 命中即进 server-mode，WS 用 cookie（浏览器会自动带上）；
  • ⑤ GET /api/whoami：页面右上角显示当前账号（可选）。

5.2 MCP 一次调用

  • ① 客户端带 Authorization: Bearer <自己的令牌> 调 MCP；
  • ② do_POST 取令牌 → _resolve_client → 首次调 /api/whoami 拿 account（进程内缓存）；
  • ③ 建会话：MCP POST /api/sessions（服务端按令牌解析身份、按账号配额判定），会话记录里钉住这把令牌；
  • ④ 后续 /step、/state、/console 全部原样透传该令牌 ⇒ 服务端每次都判同一身份；
  • ⑤ 空闲回收：用会话自己的令牌 DELETE，配额立即释放。

5.3 越权判定的折叠

越权判定的实现只有两步，且失败在 HTTP 层折叠：

// 归属校验（示意）
let owner = registry.owner_of(&session_id).ok_or_else(ApiError::session_not_found)?;
if owner != identity.account { return Err(ApiError::session_not_found()); }
// ⇒ 越权与不存在走的是同一个错误构造，status / code / detail 完全一致
折叠带来的性能副作用是好的：越权请求在进内核之前就被拒，不占会话线程、不改内核状态 —— 与被拒的非法迁移「动手之前拒绝」同一纪律。

7.4 兼容模式

兼容模式不是「降级补丁」，而是一条正式形态：没有账号库时，服务的行为必须与 v0.1.9 一致到可以被旧脚本原样复用。判据：

  • 单令牌：仍认 SIM_TOKEN（Authorization: Bearer 或 X-Auth-Token）；
  • 归属统一为 legacy：所有会话同 owner ⇒ 列表与详情行为不变；
  • 镜像根不动：/data/images/*.elf 原地可装载；
  • 页面不拦：无账号库时不 302；
  • 配额不生效：max_per_account = usize::MAX。

9.2 破例清单

本设计存在三处「故意不统一」，都必须写在这里，否则下一个改动会误以为是 bug：

  • ① 兼容头 X-Auth-Token：新代码一律走 Authorization: Bearer，但旧客户端与 MCP 内部仍可能用前者 ⇒ 两个头都要认，且判据是同一个函数。
  • ② ?token= 存在于 URL：这是 WS 的物理限制（浏览器 WebSocket 不能带自定义头），不是偷懒；范围被钉死在 /events/ws 一条路径上。
  • ③ SIM_TOKEN 在账号模式下降级为 ops：它不是管理员，看不见任何账号会话 —— 这是「不给运维默认越权通道」的取舍。
