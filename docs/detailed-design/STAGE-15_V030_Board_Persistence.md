# STAGE-15 · v0.30 冻结规格 · 板级能力闭环（D-136 + D-140 + D-141）

> **本规格是冻结的。** 实施期间只允许**订正**（依据实测），不允许**扩范围**。
> 任何与本规格不符的实现，先改规格并合回 `main`，再改代码。
>
> **契约版本：本批**不升**（`SCHEMA_VERSION` 仍是 **6**，`PLATFORM_SCHEMA_VERSION` 仍是 **1**）。
> **零新 DTO。零新命令。零新事件。**

---

## §0 定位与范围

本批的主题是**「把 v0.29 刚落地的那块板编辑器做成真正可用」**，不新增仿真能力。

### 0.1 本批做**三件**的事

| # | 事 | 闭环的欠账 | 落点 | 契约影响 |
| --- | --- | --- | --- | --- |
| **1** | **MMIO 器件参数的合法取值域** | **D-141** | **契约层** `crates/contract/src/platform.rs` 的 `validate()`（追加 V-13 ~ V-15） | 加一个场景码 `E_PLT-12` |
| **2** | **板级配置的持久化** | **D-136** | **前端** 新服务 `front/services/m23_boardstore.js`（IndexedDB 板档案） | **零** |
| **3** | **多板并存**（板档案 + 选板 / 另存为 / 删除） | **D-140** | **前端** 同上服务 + `memory-map` 视图 | **零** |

### 0.2 本批**不做**的事（明写，不是漏做）

- ❌ **不新增器件类型**（I2C 等）⇒ `DeviceSpec` 不加变体 ⇒ **不升契约版本**。
  理由：台账明写「新增器件类型 ⇒ `DeviceSpec` 加变体 ⇒ 要升 v6 → v7 ⇒ 应单独立 STAGE-15（下一批）」；
  本批先把**参数怎么校验**这件事定死（D-141），下一批加器件时才不会重想一遍。
- ❌ **不闭环 D-139**（「已装载后不能直接改板」）⇒ 仍是「存为待生效 + 重新装载工程」。
- ❌ **不提供「不生效就存起来」**（见 §2.3 裁决 B）⇒ 落库只允许**内核已接受过**的描述。
- ❌ **不持久化「未保存的草稿」** ⇒ 只持久化**用户显式保存的板档案**（见 §2.5 裁决 E）。
- ❌ **不自动跨刷新生效**（见 §2.4 裁决 C）⇒ 刷新后板**还在**，但**要重新提交**才生效。
- ❌ **不登记 D-142**（台账 §1.3 末列语义分叉）⇒ 用户已明确「只做主题本身」。
- ❌ **不做服务端形态**（P1）⇒ D-129（日志 / 健康的跨进程载体）留在下一批。

## §1 前置事实（全部实测，**不靠推演**）

### 1.1 契约层的描述校验器**已经完备** ⇒ 本批**只加规则**，不造第二个校验器

`crates/contract/src/platform.rs:262` 的 `PlatformDescription::validate()` 已实现 V-1 ~ V-9
（V-10 ~ V-12 是宿主侧的查找规则，码归契约层所有）。
**判据永远是 `family == Platform && scenario == <码>`，不看 message 文本。**

⇒ D-141 的落点**唯一**：往这个方法里**追加**规则 ⇒ 前端、宿主、契约层**共用**一个校验器（延续 STAGE-14 裁决 E）。

### 1.2 宿主的建图链路**已经完备**

`crates/kernel/src/kernel_host/platform.rs:322` 的 `map_platform()` **先 `description.validate()`、再建图**
⇒ 不合规的描述**一个区域都不留**。

⇒ 本批**宿主侧零改动**（D-141 改契约层就够；D-136 / D-140 改前端就够）。

### 1.3 ⚠️ **器件模型的寄存器布局，给器件参数划了硬上界**（实测）

这是本批最要紧的一条事实：**D-141 需要的「有依据的上界」不用拍脑袋** —— 器件模型自己的
MMIO 寄存器布局就划出了边界，**越界 ⇒ 偏移错译**（不是「浪费点内存」，是**读错寄存器**）。

**PLIC**（`crates/kernel/src/m15_peripheral/plic.rs`）：

| 区 | 偏移 | 常量 | 越界后果 |
| --- | --- | --- | --- |
| Priority | `0x0` + 4×source | `reg::PENDING = 0x1000`（:91） | `source ≥ 1024` ⇒ Priority 区**越进 Pending 区** ⇒ 源 1024 的优先级会写进 Pending 位图 |
| Pending | `0x1000` + 4×(source/32) | `reg::ENABLE = 0x2000`（:93） | — |
| Enable | `0x2000` + 0x80×ctx + 4×(source/32) | `reg::ENABLE_STRIDE = 0x80`（:95） | 每 context **只有 0x80 = 32 个字** ⇒ `ceil(sources/32) > 32` ⇒ enable 区**越进 Threshold 区** ⇒ **同一条约束的另一条路** |
| Threshold / Claim | `0x200000` + 0x1000×ctx | `reg::THRESHOLD = 0x200000`（:97）· `reg::CONTEXT_STRIDE = 0x1000`（:99） | `ctx > 15` ⇒ Claim 寄存器**落到窗口外**（窗口 `PLIC_WINDOW = 0x21_0000`，:70） |

⇒ **`sources ≤ 1024`**（两路印证：Priority 区与 Enable 区给出同一条约束）
⇒ **`contexts ≤ 16`**（默认 `DEFAULT_CONTEXT_COUNT = 16`，:83 ⇒ **正好在边界**）

**CLINT**（`crates/kernel/src/m15_peripheral/clint.rs`）：

| 区 | 偏移 | 常量 | 越界后果 |
| --- | --- | --- | --- |
| `msip` | `0x0` + 4×hart | `reg::MSIP_STRIDE = 4`（:84） | `hart ≥ 4096` ⇒ `msip` 区**越进 `mtimecmp` 区** |
| `mtimecmp` | `0x4000` + 8×hart | `reg::MTIMECMP = 0x4000`（:86）· `reg::MTIME = 0xBFF8`（:88） | `hart ≥ 4096` ⇒ `mtimecmp` 区**越进 `mtime` 区** ⇒ **同一条约束的另一条路** |

⇒ **`harts ≤ 4096`**（两路印证：`msip` 区与 `mtimecmp` 区）

### 1.4 ⚠️ **模型层会「静默纠正」非法参数**（实测）—— 这正是 D-141 必须落在描述层的原因

- `clint.rs:150`：`let harts = harts.max(1);`
- `clint.rs:155`：`freq_hz: freq_hz.max(1),`
- `plic.rs:173-174`：`source_count.max(1); context_count.max(1);`

⇒ 用户填 `freq_hz = 0` ⇒ **模型悄悄改成 1 Hz** ⇒ **用户永远不知道自己填错了**。
⇒ 台账 D-141 陷阱③明写：「**别**顺手把『取值域』做成『自动纠正』⇒ **要么原样拒、要么明确告知改成了什么**（**建议**：原样拒）」。
⇒ **本批选择「原样拒」**：描述层**原样拒**，模型层的钳制**降级为兜底**（直接构造模型的代码路径不受描述层管）。

### 1.5 ⚠️ **前端目前完全没有 IndexedDB 使用**（实测）

`grep -rn "indexedDB\|IndexedDB" front/` **只命中一条注释**（`front/views/m03_viewstore.js:46`
提到「M-23 IndexedDB persistence can read it」⇒ **那是个许愿**）。

⇒ M-23 在**前端侧**的「持久化 DataStore」是**空的** ⇒ D-136 **从零建**。
⇒ ⚠️ 本仓前端**零依赖**（AGENTS.md）⇒ **不许**引 `fake-indexeddb` ⇒ IndexedDB 适配层
**只能靠浏览器真机门禁**覆盖（见 §6.3）。

### 1.6 ⚠️ **前端没有描述校验器**（STAGE-14 裁决 E 的延续）

前端的 `front/views/components/memory-map.js` 只**呈现**约束，**不自写一份校验**。

⇒ **D-136 的核心困难**：台账 D-136 明写「存进去之前**必须**先过一遍 `PlatformDescription::validate()`，
否则库里会积攒**永远装不上的板**」⇒ **但前端没有那个校验器** ⇒
⇒ **解法见 §2.2 裁决 A**：**只有内核接受过的描述才允许落库** ⇒ 零新增校验器。

### 1.7 内置描述的实测参数（**必须全部仍合法**）

| 描述 | 器件 | 参数 | 新规则下 |
| --- | --- | --- | --- |
| `default.json` | `gpio` | — | 无数值参数 ⇒ **无新规则** |
| `minimal.json` | — | 无器件 | **无新规则** |
| `qemu-virt.json` | `clint` | `freq_hz = 10000000`、`harts = 1` | ✅ `freq_hz ≤ 1e12` ✓、`harts ≤ 4096` ✓ |
| `qemu-virt.json` | `plic` | `sources = 64`、`contexts = 16` | ✅ `sources ≤ 1024` ✓、`contexts ≤ 16` ✓（**正好在边界**） |
| `qemu-virt.json` | `uart16550` | `irq_line = 1`、`baud_rate = 115200` | ✅ `irq_line(1) < min(sources=64)` ✓、`baud_rate ≥ 1` ✓ |
| `qemu-virt.json` | `gpio` | — | ✅ |

⇒ **三个内置描述在新规则下全部合法** ⇒ 收紧校验**不会**让内核自带的板失效。

### 1.8 宿主的 `on_set_memory_map` 的**事件载荷是「当前生效的图」**，不是「用户配的那份」

`crates/kernel/src/kernel_host/mod.rs:2070`：`validate()` → 记 `user_board` → 未装载则立即生效
→ 回 `EventPayload::MemoryMap { description: self.platform.clone(), pending }`。

⇒ **前端拿不到「内核接受了我的板」这件事的描述** ⇒ 但**能**拿到「这条命令**没有**回错误事件」这件事
⇒ 这就是 §2.2 裁决 A 的**判据**。

### 1.9 契约层的 `E_PLT` 族**还有一个空号**

`crates/contract/src/error.rs:391`：`E_PLT_11_PLATFORM_FILE_MALFORMED` 是最后一个 ⇒
**`E_PLT_12` 空闲** ⇒ D-141 用它（台账 D-141 做法 B 明写「`E_PLT-12` **空闲** ⇒ 正好」）。

## §2 歧义处置

### 2.1 板档案存在哪 —— **前端 IndexedDB**（裁决 A）

台账 D-136 给两条路：**建议 A**（前端 IndexedDB 存描述 JSON ⇒ 不改契约、不改宿主、刷新即恢复 ⇒ 约 1~2 人日）
与**建议 B**（宿主侧存档 + 新命令 ⇒ 要再升一次版本 ⇒ 约 3~4 人日）。

⇒ **本批走建议 A**。理由三条：
1. 台账自己的建议顺序就是「**A → C → B（建议 A）**」；
2. 「板」的生命周期（比会话长、比工程短）**属于前端**的事 ⇒ 放宿主会话内是**放错了层**（D-136 的根因）；
3. 走建议 B 要**再升一次契约版本**（v6 → v7）⇒ 与本批「不升版本」的定位冲突。

⚠️ **建议 A 的代价**：落库的内容**只由前端保证**，前端崩溃 / 换机器就没了 ⇒
**这是「一块板」的合理语义**（工程文件同理）⇒ 但必须在界面上说清楚（「板档案存在**本机浏览器**里」）。

### 2.2 落库的门槛 —— **只有内核接受过的描述才允许落库**（裁决 B）

⚠️ **这是本批最关键的一个决定**，因为前端**没有**校验器（§1.6）。

- **落库时点** = `SetMemoryMap` 命令**成功往返**（内核**没有**回错误事件）⇒ 内核的 `validate()` 已经过了。
- ⇒ **库里不会有永远装不上的板** ⇒ 台账 D-136 的核心担心被**结构性**化解，**不靠前端写第二份校验器**。
- ⇒ 前端要记一件事：「**当前草稿已被内核接受过**」⇒ 这是一个**推导量**
  （与宿主的 `pending` 同一个思路：*一个约束一个落点*）。
  ⇒ ⚠️ **施工期订正**（Lane C 实测指出初版这句**自相矛盾**）：初版在这里写
  「**改动即失效**（用户改了草稿 ⇒ 标志清掉）」——**「推导量」与「标志清掉」是两种
  机制**：前者**没有标志**可清 ⇒ **按推导量实现**：
  **判据 = 「内核接受过的那份描述快照」非空 且 与「当前草稿转成的描述」逐字段相同**
  ⇒ 用户改了草稿 ⇒ 逐字段不再相同 ⇒ **自动**不再算「已接受」⇒ **不需要手工失效逻辑**
  （手工失效 = 第二个真相）。

⚠️ **为什么不加一条「只校验不生效」的命令**（那本来最干净）：
⇒ 那是一条**新命令** ⇒ **契约要升 v6 → v7** ⇒ 与本批定位冲突 ⇒ ⇒ **不加**（裁决 G）。

### 2.3 「保存」与「另存为」的语义 —— **保存 = 落库；生效 = 提交**（裁决 C）

- 「**提交板级内存图**」（v0.29 已有）⇒ 提交给内核 ⇒ 立即生效 / 挂起待生效。**本批一个字不改**。
- 「**保存当前板**」⇒ 把**当前草稿**写进板档案（键 = 草稿的 `id`）⇒ **不改内核状态**。
- 「**另存为板**」⇒ 以当前草稿为模板**新建**一块板 ⇒ 用户给**新的 `id`** + 新的 `name` ⇒ 写进档案。
- ⇒ **落库门槛**（裁决 B）：两者都要求「当前草稿已被内核接受过且此后未被改动」⇒
  **否则按钮禁用**，并明说「先提交，校验通过后才能保存」。
- ⚠️ 「另存为」只改 `id` / `name` ⇒ **其余字段逐字相同** ⇒ 合法性必然相同
  （V-2 只要求 `id` 非空 ⇒ 新 `id` 非空即可）⇒ **不需要第二次提交**，也**不需要第二次校验**。
- ⇒ **本批不提供「不生效就存起来」**（§0.2）⇒ 这是「零第二份校验器」的**代价**，明写在此。

### 2.4 刷新之后怎么办 —— **不自动重新提交**（裁决 D）

刷新 ⇒ 前端重连内核 ⇒ 内核的 `user_board` / `self.platform` 还在（同一个 Worker）⇒
事件 `memory.map` 推当前图 ⇒ **界面显示的图没丢**。

⚠️ 但**前端侧**的板档案在 IndexedDB ⇒ **刷新后还在** ⇒ 用户能再选、再提交。

⇒ **决定**：刷新后**只**恢复「板档案列表」⇒ **不自动提交**。
  ⚠️ **施工期订正**（Lane C 实测指出初版**不可实现**）：初版写「恢复『板档案列表』与
  『上次选中的板被高亮』」，但 **B-8 把条目字段集合钉死为 `id` + `description`**
  且 §3.3 只冻结**一个** objectStore ⇒ **无处存选中项** ⇒
  ⇒ 口径改为「**选中项不跨刷新保留**」⇒ **不为存一个选中项去动 B-8 的字段集合**
  （那是本批的确定性契约）。
理由：自动提交在「已装载镜像」时会变成「挂起待生效」⇒ 用户刷新一次就多一次「改了板没反应」的困惑
（**正是 D-139 那面墙**）⇒ **不做自动动作**更诚实。

⇒ **口径写清**：「刷新后板**还在**（内容逐字段相同）⇒ 但**要重新提交**才生效」
⇒ 这是 D-136 的**闭环口径**，**不是**「刷新即自动生效」。

### 2.5 板档案的主键 —— **描述的 `id`**；已有板的 `id` **只读**（裁决 E）

台账 D-140 做法 A：「用描述里的 `id` 字段当主键 —— 契约层已有 `id`，且 V-2 已保证它非空 ⇒ **零新 DTO**；
⚠️ 但 `id` 是**用户可改**的 ⇒ 改了就是「另一个板」⇒ 要么把 `id` 定成**不可改**，要么另给一个**稳定 id**」。

⇒ **本批选「`id` 只读」**（不新增 DTO 字段，不与 STAGE-14 裁决 H 冲突）：
- **编辑已有板时**：`id` 输入框**只读** ⇒ 「改 `id` 的入口**不存在**」。
- **另存为时**：必须给一个**新的 `id`** ⇒ 新板另存、旧板仍在 ⇒ 与台账判别力②同形。
- ⇒ 板档案条目 = `{ id, description }` ⇒ **不另存 `name`**（`name` 在描述里）⇒ **不存时间戳**
  （⚠️ 确定性：AD §8.1 D0「种子 + 时间戳化输入事件序列 → 结果唯一」⇒ 落库内容里**不引入**时间戳）。

⚠️ **前端唯一会判的事**：**档案里 `id` 不重复**（台账 D-140 做法 A 的「唯一 id」）。
⇒ 这**不是**描述合法性 ⇒ **不违反** STAGE-14 裁决 E（裁决 E 管的是「描述合法性由内核裁决」）。

### 2.6 D-141 的上界从哪来 —— **器件模型的寄存器布局**（裁决 F）

台账 D-141 陷阱④：「**上限值要有依据（不是拍脑袋）**」；
陷阱⑤：「`irq_line` 的上限应当等于 **PLIC 的源数** ⇒ 而 PLIC 的源数**在另一个区域里** ⇒
**落点**要想清楚」。

⇒ **上界全部来自 §1.3 的实测布局**，不是拍脑袋：

| 参数 | 下界 | 上界 | 依据（实测） |
| --- | --- | --- | --- |
| `uart16550.irq_line` | 0（u16） | 见 V-15（跨字段） | PLIC 源 id 是 0-based，个数为 `sources` ⇒ 合法 id 是 0 ≤ id < sources |
| `uart16550.baud_rate` | **≥ 1** | **不判** | 0 波特率无物理意义；**架构没有上界** ⇒ 不拍数字 |
| `clint.freq_hz` | **≥ 1** | **≤ 1 000 000 000 000**（1 THz） | 平台最小时间粒度是 **1 ps**（`PS_PER_SEC = 1e12`，`clint.rs:72`）⇒ 频率高于 1 THz ⇒ **一个周期短于 1 ps** ⇒ 平台表达不了（`ps_per_cycle()` 会算成 0，`clint.rs:183`） |
| `clint.harts` | **≥ 1** | **≤ 4096** | `msip` 区 `0x0 + 4×hart` 不越进 `mtimecmp` 区 `0x4000`；`mtimecmp` 区不越进 `mtime` 区 `0xBFF8` ⇒ **两路印证** |
| `plic.sources` | **≥ 1** | **≤ 1024** | Priority 区 `0x0 + 4×source` 不越进 Pending 区 `0x1000`；Enable 区每 context 32 字 ⇒ **两路印证** |
| `plic.contexts` | **≥ 1** | **≤ 16** | Threshold / Claim 区 `0x200000 + 0x1000×ctx` 落在窗口 `0x210000` 内 ⇒ `ctx ≤ 15` + Claim 的 4 字节 ⇒ **≤ 16** |

⚠️ **`harts` 的诚实说明**：本仓的 ISS 是**单 hart** ⇒ `harts > 1` 时多出来的 hart **没有执行器**
（它们的 `mtimecmp` 永远不会被写）⇒ 这是**如实的能力边界**，**不是错误** ⇒ **不因此判非法**。

### 2.7 `irq_line` 的跨字段规则 —— **图中有 PLIC 才判**（裁决 G）

- 图中**有** PLIC ⇒ 每个 `uart16550.irq_line` 必须 `< min(所有 plic.sources)`
  （**取最小** ⇒ 对**每个** PLIC 都合法 ⇒ 保守且无歧义）。
- 图中**无** PLIC ⇒ **不判**。理由：**没有 PLIC ≠ 这块板非法**；只是这块板没有中断路由，
  `irq_line` 因此**无意义但无害** ⇒ 不该因此拒掉一块合法的板。

⇒ 这条规则的**判断依据跨区域**（UART 在一个区域、PLIC 在另一个区域）⇒ **落点就是契约层那个校验器**
⇒ **一个约束一个落点** ✓。

### 2.8 错误码 —— **`E_PLT_12` 一个码覆盖两类越界**（裁决 H）

- 单字段越界（`baud_rate = 0`、`freq_hz = 0`、`sources = 0`、超上界……）
- 跨字段越界（`irq_line` 不在 PLIC 源数之内）

⇒ 二者**含义一致**：「**某个器件参数的值不在它的合法取值域内**」⇒ **一个码**。
⇒ **不**复用 `E_PLT_08`（那是「器件 `id` 重复」⇒ 一个码两个含义 ⇒ 禁止）。
⇒ **不**新增第二个码（否则两个含义几乎相同的码 ⇒ 用户看不懂）。

⇒ **消息里说清是哪个字段、为什么**（给人看）⇒ 但**判据永远是 `family` + `scenario`**（§1.1）。

### 2.9 版本 —— **两个版本都不升**（裁决 I）

| 版本 | 值 | 动吗 | 理由 |
| --- | --- | --- | --- |
| `SCHEMA_VERSION`（契约信封） | 6 | **不动** | **零新 DTO、零新命令、零新事件** ⇒ 载荷形状一字未改 |
| `PLATFORM_SCHEMA_VERSION`（描述格式） | 1 | **不动** | 描述的**线上形状**一字未改；被改的是**合法性**（哪些描述被接受），不是「描述长什么样」 |

⚠️ **代价（如实写明）**：旧前端 + 新内核 ⇒ 内核可能回 `E_PLT_12` ⇒ 旧前端**不认识这个码** ⇒
它显示原始码 + 内核给的中文消息 ⇒ **不崩**（前端只显示 `error.code` 与 `error.message`，本仓前端**没有**错误码表）。

### 2.10 本批内部的**次序** —— **D-141 先落，D-136 后落**（裁决 J）

台账 D-141 破坏性变更预警明写：「**先做 D-141 再做 D-136**」，理由是「未来做持久化时这条会变成真问题」。

⇒ 本批**两条都做** ⇒ 必须把次序**显式定死**：
1. **D-141 先落**（契约层）⇒ 描述的合法性规则**先定死**；
2. **D-136 后落**（前端）⇒ 板档案是**本批才有的新存储** ⇒ 库里**不可能**有「旧规则下合法、新规则下非法」的存量
   （因为库里每一条都是**新规则下**内核接受过的）⇒ **存量风险为零** ✓。

⇒ ⚠️ **给未来的规矩**：**再收紧**合法性规则时，库存量**会**变成真问题 ⇒ 那时必须给迁移口径
（迁移 / 标记失效 / 拒绝加载并提示）⇒ 记进 §7。

### 3.1 契约层（**唯一**改动面）

```rust
/// 场景码：某个器件参数的值不在它的合法取值域内。
```

```rust
// crates/contract/src/platform.rs —— validate() 追加三条规则
// ⚠️ 追加在 V-9 **之后** ⇒ V-1 ~ V-9 的**报告顺序一个字不变** ⇒ 既有判别力不受影响。

// V-13 —— 器件参数的**下界**（单字段）
//   uart16550.baud_rate >= 1
//   clint.freq_hz     >= 1
//   clint.harts       >= 1
//   plic.sources      >= 1
//   plic.contexts     >= 1
//   ⇒ E_PLT_12

// V-14 —— 器件参数的**上界**（单字段，依据 = 器件模型的寄存器布局）
//   clint.freq_hz <= 1_000_000_000_000
//   clint.harts   <= 4096

//   plic.contexts <= 16
//   ⇒ E_PLT_12

// V-15 —— 跨字段：irq_line 必须落在 PLIC 的源数之内
//   图中有 PLIC ⇒ irq_line < min(所有 plic.sources)
//   图中无 PLIC ⇒ 不判
```

⚠️ **上界常量放哪**：**契约层**（与 `PLATFORM_SCHEMA_VERSION` 同处）⇒ M-15 / 宿主若要用，**只引用不复制**
（延续 v0.22 `MSTATUS_WARL_MASK` 的做法）⇒ **全仓一个定义处**。

⚠️ **`gpio` 没有数值参数** ⇒ **一条新规则都不适用** ⇒ `gpio` 的 `id` 非空**已由 V-2 覆盖**（V-2 判的是**描述**的 `id`，
⚠️ **注意**：V-2 判的是**描述的 `id`**（`PlatformDescription.id`），**不是**器件的 `id` ⇒
**器件 `id` 为空**目前**没有任何规则覆盖** ⇒ ⚠️ **本批补一条？**
⇒ **裁决**：**补** —— 器件 `id` 为空 ⇒ 该器件在快照回灌时**没有身份** ⇒ `E_PLT_12`？
⇒ ⚠️ 不 ⇒ **空器件 id 不是「取值域」问题**，是「非空性」问题 ⇒ 复用 `E_PLT_02`？那个是「描述 id 为空」⇒ **一个码两个含义** ⇒ 禁止。
⇒ ⇒ **本批不动它**（不在 D-141 的范围内）⇒ 记为**遗留**，见 §8.3。

### 3.2 宿主 —— **零改动**

理由：`map_platform()` 已经先校验后建图（§1.2）⇒ 契约层加规则，宿主**自动**生效。

### 3.3 前端服务层 —— **新增** `front/services/m23_boardstore.js`（冻结 API 形状）

⚠️ **纯逻辑与存储分离** ⇒ 纯逻辑可在 `node:test` 里直接测（前端零依赖 ⇒ 不用 `fake-indexeddb`）。

```js
// ---- 常量 ----
export const BOARD_DB_NAME = "riscv-sim-board-store"; // IndexedDB 库名（**独立** ⇒ 不碰别的库）
export const BOARD_DB_VERSION = 1;                // 库版本
export const BOARD_STORE_NAME = "boards";         // objectStore 名
export const BOARD_STORE_KEY = "id";              // 主键 = 描述的 id

// ---- 纯逻辑（与存储无关 ⇒ 可测）----
// 落库条目：{ id, description }（⚠️ 不存时间戳 ⇒ 确定性）
export function boardId(description) -> string|null
export function boardEntry(description) -> {id, description}|null
export function mergeBoard(archive, entry) -> {archive, changed}
export function dropBoard(archive, id) -> {archive, changed}
export function findBoard(archive, id) -> entry|null
export function isBoardIdTaken(archive, id) -> boolean
export function checkBoardVersion(description) -> {ok:true}|{ok:false, reason:"version", expected, actual}

// ---- 存储适配层（backend 可注入 ⇒ 测试用内存实现）----
export function createMemoryBackend() -> backend
export function createIndexedDbBackend() -> backend
export function createBoardStore(backend) -> {list, put, remove, clear}
```

**backend 契约**（**四个**方法 —— 施工期订正，见 §11）：

```js
backend.list()   -> Promise<entry[]>      // 读全部（按 id 升序）
backend.put(entry) -> Promise<void>       // 按 entry.id 写入（覆盖）
backend.remove(id) -> Promise<void>       // 按 id 删除
backend.clear()  -> Promise<void>         // 清空全部
```

⚠️ **`clear()` 必须在契约里**（施工期订正）：初版只写了三个方法，
但 `createBoardStore` 的门面暴露了 `clear()` ⇒ **契约与方法集不自洽** ⇒
要么把契约补成四个，要么门面不做 `clear`。⇒ **补成四个**（加法 ⇒ 不破坏任何已有实现）。
⚠️ `createBoardStore.clear()` **优先调 `backend.clear`**；若某个 backend 没实现它，
**退化成「逐条 remove」** ⇒ 三方法的老 backend 仍然可用。

⚠️ **`createIndexedDbBackend()` 在不支持 IndexedDB 的环境要能「明确地失败」**
⇒ 返回 `{ supported: false, reason }` ⇒ 前端**降级为「只在本会话内」**并**显式提示**（不静默假装成功）。

⚠️ **存储不可用时，写操作要「明确地失败」**（施工期订正）：
`list()` ⇒ `[]`（能读，只是空的）；**`put` / `remove` / `clear` ⇒ 明确地抛错**
⇒ **不许**变成「静默的空操作」⇒ 否则用户以为存上了、其实没存。
⇒ 因此 `createBoardStore(backend)` 的返回值**附加**一个布尔标志 `supported`
（`true` / `false`）⇒ 视图层**先判后调**（见 §3.5）。

⚠️ **描述格式版本常量的落点**（施工期订正 ⇒ 裁决 K）：
`PLATFORM_SCHEMA_VERSION`（= 1，描述格式版本，**不是**契约信封的 `schema_version` = 6）
**唯一**定义在 **`front/lib/message.js`**（前端契约镜像层）⇒
`front/views/components/memory-map.js` 与 `front/services/m23_boardstore.js`
**都从那里 import** ⇒ **一个定义处**。
⚠️ 初版规格让服务层「自己另立一个同值常量」⇒ 那是**两个真相**（同一个值两处定义 ⇒ 漂移）
⇒ **不接受** ⇒ 由**统筹方**在集成时上移（服务层与视图层都改 ⇒ 跨 lane ⇒ 统筹方做）。

### 6.2 变异方法论（不变）

- 必须能编译；期望集合 **AND** 语义；记录**完整红集**；
- 还原用 `cp` + `md5` + `cmp` + `touch`；**禁** `git checkout -- <file>`；
- 变异期间**不改**其它被编译源文件；必须有超时（本机 macOS 无 `timeout` ⇒ 用 `tools/watchdog.pl`）。

### 6.3 ⚠️ 本批的**覆盖缺口**（明写）

**IndexedDB 适配层只有浏览器真机门禁覆盖**（T-3）—— 因为前端**零依赖** ⇒ 不能引 `fake-indexeddb`。

**真实 IndexedDB 那一层靠 T-3** ⇒ ⚠️ 两者都要跑才算绿。

### 6.4 ⚠️ macOS 的坑（不变）

**新链接出来的测试二进制，第一次 `exec` 会被安全评估卡住**（实测 51 秒墙钟 / 0.012 秒 CPU）
⇒ 每轮改源码后**串行**预热全部测试二进制（**勿并行**）⇒ 再跑正式测试。
