1 功能概述

1.1 模块定位

M-05 命令路由与事件分发（4.2.2）：实现 Command Bus 与 Event Bus——命令（C1/CF1）带请求 id 路由、超时 ≤500ms、读类/幂等命令可重试；事件按订阅分发，E1 关键控制事件（breakpointHit/trap/paused）可靠投递（ack/重试），观测类事件允许丢失并由前端对账。执行协议版本协商（只增不改、未知字段忽略、不兼容明确拒绝并提示升级路径）。承载背压治理（订阅队列水位 80%，降采样/丢最旧，与 M-19 对齐，评审 P-10）。预留 headless 网关接入（REST/CLI 命令面，FR-16，P1）。在各层边界做轻量调用链打点（进入/离开耗时采样，仅管理员通道可见，评审 P-20）。

1.3 MVP 范围与预留

MVP 实现范围：dispatchCommand(cmd)（校验能力 → 分发 → 超时管理）、publish(event)（关键/观测分级分发）、subscribe(channel, sub)/unsubscribe、negotiate(version, caps)（协议版本与能力协商）、setWatermark(ratio)（背压水位）、traceSpan(layer, tEnter, tLeave)（层边界打点）。

2 数据描述

2.1 核心数据结构（源文档表32）

数据结构类型定义与用途
cmdRegistryMap<cmd, handler>命令处理器注册表（路由目标，非法命令返回 E_CTX-05 未注册路由）

2.1.1 复杂结构字段定义

cmdRegistry 按命令名路由到目标模块处理器；subTable 按通道维护订阅者集合（订阅句柄供退订引用）；seqCounter 单调递增作为断线续拉锚点（对齐 E_PROTO-05 序列号缺口语义）；capBits 记录 ExecutionBackend 分级协商结果（L1/L2/L3，QEMU 仅 L1 子集降级）。字段定义如下：

// ProtocolMessage: 协议消息结构（DTO，语言无关 JSON Schema/IDL，2.3 事件结构对齐）
struct ProtocolMessage {
  uint32_t msgType;         // 消息类型枚举（命令/响应/事件）
  uint64_t reqId;           // 请求 id（命令路由配对，Resp 回带）
  uint64_t seq;             // 协议序列号（seqCounter，断线续拉锚点）
  uint8_t  version;         // 协议版本（negotiate 协商，只增不改）
  json     payload;         // 载荷（必填/可选字段 + 校验规则）
};
// Resp: 命令响应（请求 id 配对，超时 ≤500ms）
struct Resp { uint64_t reqId; err_t err; json payload; };
// Event: 事件对象（S1/W1/T1/E1：事件类型 + 载荷字段 + 序列号语义）
struct Event {
  uint8_t  kind;            // 关键控制（E1: breakpointHit/trap/paused）或观测类（05-4 分级规则）
  uint64_t seq;             // 单调序列号（断线续拉缺口）
  json     payload;         // 载荷字段（schemaVersion 由协议版本协商管理；事件流持久化由 M-23 DataStore 归档，05-9 已核对）
  uint8_t  channel;         // 订阅通道（05-5 枚举：0=debug / 1=state / 2=trace / 3=log）
};
// channel 枚举（05-5）：0=debug（断点/单步等调试命令事件）、1=state（simStateDelta/watchUpdate 状态类）、2=trace（trace 记录/反汇编观测）、3=log（日志/告警）
// 订阅句柄（05-5）：subscribe 返回 uint32 句柄 id（subTable 索引引用，退订/对账使用）
// evHistory: 事件历史环形窗口（05-7，按 seq 索引，最近 N=10^4 条；断线续拉 E_PROTO-05 的数据源，溢出丢最旧）
struct evHistory { ring<Event> cap=10000; uint64_t minSeq; };   // minSeq=窗口内最小序列号（续拉下界）
// NegotiateResult（05-9）：协商结果两态展开——{ok, capBits result}（兼容/降级明确）或 {reject, E_PROTO-01, upgradePath}（不兼容拒绝 + 升级提示）
// capBits: 能力位集合（含 ExecutionBackend L1/L2/L3 分级协商结果）
struct capBits { bool L1; bool L2; bool L3; };   // QEMU 仅 L1 子集（E_CTX-03 降级）
// layerSpans: 调用链耗时采样（进入/离开，仅管理员通道可见，评审 P-20）
struct layerSpans { ring<{layer, tEnter, tLeave, durNs}>; uint32_t cap; };

2.3 数据流说明

命令流：前端（M-01~M-03）onCommand → M-05 dispatchCommand（版本/能力校验 → 路由 → 执行）→ Resp（请求 id 配对，超时 ≤500ms，读类/幂等可重试）。
事件流：仿真/调试事件源（M-08~M-19）产生 → publish 分级（关键 E1：breakpointHit/trap/paused 走可靠通道 ack/重试；观测类按节流）→ 按 subTable 分发 → 订阅方消费（M-03 View Store 刷新 ≤200ms 合并）。
序列语义：seqCounter 每消息递增，断线续拉按缺口补齐（E_PROTO-05）。

3 实现设计

3.1 dispatchCommand(cmd) 命令路由

dispatchCommand(cmd)：接收 ProtocolMessage → 版本/能力校验 → 按 cmdRegistry 路由 → 目标模块处理器执行 → Resp（请求 id 配对，超时 ≤500ms，读类/幂等命令可重试）。伪代码如下：

// dispatchCommand: 命令路由（4.2.2.3 表33；校验能力 → 异步可中断超时分发 → Resp）
Resp dispatchCommand(ProtocolMessage cmd) {
  if (cmd.version != negotiated) return E_PROTO-01;   // 协议版本不匹配（拒绝 + 升级提示）
  if (cmd.msgType not in cmdRegistry) return E_CTX-05; // 未注册路由
  if (!capBits.allows(cmd)) return E_CTX-03;          // 能力不足（QEMU 下 L2/L3 → 拒绝 + 协商降级，05-10）
  Resp r = dispatchWithTimeout(                       // 异步可中断超时（05-2）：定时器驱动
    cmdRegistry[cmd.msgType].handler, cmd, 500ms);    // 超时即返回 E_CTX-06 并作废处理器结果
  if (r.timedOut) return E_CTX-06;                    // 命令超时（读类/幂等可重试；写类不自动重试防副作用，6.2(1)）
  r.reqId = cmd.reqId; return r;                      // Resp 请求 id 配对
}

3.2 publish(event) 事件分级分发

publish(event)：按分级规则（05-4：E1 关键清单走可靠通道，其余观测类节流）分发；deliver* 即最终投递（内部经 subTable 单次分发，05-1 单投递模型）；可靠通道队列上限 64/ack 500ms/重试 ≤3 次（05-6）；观测类超水位降采样/丢最旧（与 M-19 对齐，P-10）。伪代码如下：

// publish: 事件按订阅分发（4.2.2.3 表33；分级 → 单投递 → 背压）
void publish(Event ev) {
  ev.seq = seqCounter++;                             // 单调序列号（断线续拉锚点，同时入 evHistory 窗口）
  evHistory.push(ev);                                // 05-7：环形窗口（10^4 条按 seq 索引，续拉数据源）
  if (ev.kind == CRITICAL) {                         // E1 关键控制事件（breakpointHit/trap/paused）
    deliverReliable(ev);                             // 05-6：队列上限 64、ack 超时 500ms、重试 ≤3 次
  } else {                                           // 观测类（watchUpdate/simStateDelta/checkpoint/trace 等）
    if (queueLevel(ev.channel) >= queueWatermark)    // 队列超水位（默认 0.8，P-10）
      downsampleOrDropOldest(ev);                    // 降采样/丢最旧（与 M-19 对齐）
    deliverThrottled(ev);                            // 节流投递（可丢失，前端对账）
  }
  // 05-1：deliver* 即最终投递（内部经 subTable 单次分发）；无外层 notify 循环（防双投递）
}
// deliverReliable（05-1/05-6）：可靠通道最终投递——入可靠队列（上限 64）→ 经 subTable 单次分发 →
//   订阅方 ack（500ms 超时）→ 未 ack 重试（间隔 100ms，≤3 次）→ 仍失败 → 前端对账（E_PROTO-07）
// deliverThrottled：观测类最终投递——经 subTable 单次分发，超水位先降采样/丢最旧

3.3 negotiate(version, caps) 协议版本与能力协商

negotiate(version, caps)：协议版本协商（只增不改、未知字段忽略、不兼容明确拒绝并提示升级路径）；能力协商（backendCapBits 来源=M-17 执行后端能力位查询，05-3；ExecutionBackend L1/L2/L3，QEMU 仅 L1 子集降级，E_CTX-03）。返回 NegotiateResult 两态结构（05-9）。伪代码如下：

// negotiate: 协议版本与能力协商（4.2.2.3 表33）
NegotiateResult negotiate(uint8_t version, capBits caps) {
  if (version > CURRENT_VERSION) {                   // 只增不改：向后兼容
    return {ok, CAPS_UNCHANGED};                     // 未知字段忽略（E_PROTO-02 仅日志）
  }
  if (version < MIN_SUPPORTED)                       // 不兼容（低于最低支持版本）
    return {reject, E_PROTO-01, upgradePath};        // 明确拒绝 + 提示升级路径
  capBits backend = m17GetCaps();                    // 05-3：backendCapBits 由 M-17 执行后端暴露（BackendVtbl.caps）
  capBits result = caps & backend;                   // 能力位协商（QEMU 仅 L1 子集降级）
  return {ok, result};                               // 输出：协商结果（降级明确，05-9 NegotiateResult）
}
// NegotiateResult 两态（05-9）：{ok, capBits result}（兼容：含降级后能力位）| {reject, E_PROTO-01, upgradePath}（不兼容拒绝 + 升级提示）
// 降级路径（05-10）：E_CTX-03 拒绝响应携带建议能力位 → 前端按 capBits 主动降级后重发 negotiate；或调用方按拒绝响应升级路径处理

5 处理流程

5.1 命令路由与事件分发流程（源 4.2.2.4 对齐）

双链路：命令流 = 接收 → 版本/能力校验 → 路由 → 执行 → Resp（超时 ≤500ms）；事件流 = 产生 → 分级（关键/观测）→ 按订阅分发 → 节流/可靠投递；队列超水位 → 降采样/丢最旧；层边界进入/离开打点采样（管理员可见）。

分支：命令超时 → E_CTX-06（幂等可重试）；能力不足 → E_CTX-03 协商降级；协议不兼容 → E_PROTO-01 拒绝 + 升级提示；队列超水位且降载仍堆积 → 暂停非关键订阅并告警（背压保护，P-10）。

5.2 与相邻模块的协作说明

协作模块协作内容触发时机

6 异常处理

6.1 错误码与处置（E_CTX 族主属方 + E_PROTO 族）

M-05 为 E_CTX 错误码族主属方（源文档 3.4 表16），命令/事件路径的错误码统一收敛于此；协议层错误归 E_PROTO 族（一场景一码）：

错误码 / 场景触发条件处置
E_CTX-05 未注册路由命令 msgType 不在 cmdRegistry拒绝并返回（hash 路由兜底页语义）
E_CTX-06 命令超时Resp 超时 ≤500ms超时错误（幂等可重试）
E_CTX-03 能力不足QEMU 下调用 L2/L3 能力拒绝并协商降级（capBits 协商）
E_PROTO-01 协议版本不匹配版本低于最低支持明确拒绝 + 提示升级路径
E_PROTO-02 未知字段收到未知字段（向后兼容）仅日志，忽略（只增不改）
E_PROTO-05 序列号缺口断线续拉发现缺口按序列号续拉；无法补齐 → 前端全量状态对账
E_PROTO-07 关键事件 ack 超时E1 可靠通道 ack 超时重试投递；重试失败 → 前端对账
E_PROTO-08 消息格式错误报文格式非法拒绝并记录原始报文摘要（脱敏）

E_CTX-09 headless 未启用gatewayDispatch 未启用（P1 预留）返回 E_CTX-09（FR-16 未开启）

6.2 边界与降级

（1）命令超时：E_CTX-06。执行模型=异步可中断超时（05-2）：dispatchWithTimeout 定时器驱动，500ms 未返回即回 E_CTX-06 并作废处理器结果；读类/幂等命令可重试，写类命令不自动重试（防副作用重复）。

（2）能力不足：E_CTX-03，拒绝 + 协商降级（05-10 降级路径：拒绝响应携带建议能力位 → 前端按 capBits 主动降级后重发 negotiate；或调用方按拒绝响应升级路径处理。QEMU 仅 L1 子集）。

（3）协议版本：只增不改、未知字段忽略（E_PROTO-02 仅日志）；不兼容明确拒绝 + 升级路径（E_PROTO-01）。

（4）背压：队列水位 0.8 超限 → 降采样/丢最旧（与 M-19 溢出策略一致）；降载仍堆积 → 暂停非关键订阅并告警（P-10）。

（5）关键事件可靠投递（05-6 参数）：队列上限 64、ack 超时 500ms、重试间隔 100ms、重试 ≤3 次；队列满或重试耗尽 → 前端对账（E_PROTO-07，关键事件不丢，表91）。

（6）序列号缺口：数据源=evHistory 环形窗口（最近 10⁴ 条、按 seq 索引，05-7），按缺口 seq 续拉补齐；窗口外缺口 → 前端全量状态对账（E_PROTO-05）。

（7）打点采样：仅管理员通道可见（P-20），产品/嵌入式工作台不可见（角色边界）；layerSpans 环形溢出丢最旧（05-10）。

7.2 可维护性手段

（1）注册表驱动：cmdRegistry 按命令名登记目标模块处理器，新增命令只登记不改造核心路由（协议只增不改扩展点，表93）。

（2）分级分发解耦：关键事件可靠通道与观测类节流通道独立实现，可分别单测（可靠投递/背压语义）。

（3）协议版本化：negotiate 只增不改 + schemaVersion 迁移（事件流持久化配合 M-23 DataStore 归档），契约变更走版本协商不破坏性替换（源 2.5 引用规则③）。

（4）打点可关：traceSpan 采样入 layerSpans 环形缓冲，仅管理员通道查询，不影响业务路径（P-20）。

（5）CI 门禁：核心模块单测覆盖率 ≥70%（估算基线，源文档 7.3 表92）；命令路由/事件分发用例纳入确定性夹具。

（6）契约层可替换性（源 2.5 对齐）：本模块对外 driving 端口收敛到 9.1.1 端口契约，替代实现遵守同端口契约并通过契约测试即可接入。

9.2 日志对接（M-21）
