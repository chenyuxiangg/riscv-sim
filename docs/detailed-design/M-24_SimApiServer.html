1 功能概述

1.1 模块定位

M-24 是 riscv_sim 的进程级对外操作入口：把内核已有的能力（装载 / 运行 / 步进 / 断点 / 寄存器 / 内存 / 反汇编 / console 字节流）以稳定的 HTTP + WebSocket 形态暴露，使 Agent / CI 不必 import front/assets/pkg/riscv_sim_kernel.js，也不必知道 front/ 的目录结构。

它不是第 24 个内核模块：M-13 仍然解释指令，M-12 仍然持有虚拟时钟，M-14 仍然管理映射，M-08 仍然持有断点表。M-24 只做四件事 —— 传输（HTTP/WS）、会话（表 + 生命周期 + 隔离）、缓冲（console 的绝对 offset）、映射（内核码 ↔ HTTP 状态）。浏览器形态里住在 M-04/M-05/M-07 的三块职责，在服务端形态里由 M-24 承担；内核与契约层不动。

三条设计红线（与需求的「非目标」逐条对齐）：

  • 不替代浏览器工作台：前端仍是主交互面，M-24 是第二个入口，两者共用同一份内核与契约。
  • 不在 API 层改内核语义：无板不装载、镜像落在板外即拒、ISA 门禁不过即拒 —— 一律原样透出，不做「贴心兜底」。
  • 不给同一个故障造第二个码：错误码只在契约层拥有，M-24 只补 HTTP 状态与 detail。

2.3 数据流与缓冲

一条命令的完整路径：HTTP handler 组 Message → mpsc 投递给会话线程 → KernelHost::handle_message 执行 → 事件分批返回 → 先把 Console 字节 append 进 ring、再按停因组响应。「先日记账、后作结论」是 R-06 与 R-05 一致性的关键：响应里说的字节数必须此刻已经可读。

需求收口的落地口径（v1.8）：① 复位用会话自己记下的「最后一次成功装载」镜像（name / kind / bytes）重装 —— 同一块板、同一订阅；pc 回 entry、executed 归零（LoadProject 重置计数）；console 环不裁（R-06 只追加），回执带 {base,total} 让客户端对齐；没装过镜像 ⇒ 409 E_SESS-02。② 前缀：服务端按 1 000 条小窗口推进并逐窗扫 console 字节（内核对 console 内容一无所知）⇒ stop_reason=prefix；明口径：executed 相对真实停点最多多算一个窗口；没给 steps 时默认预算 1e6。③ until：breakpoint / halt；前者把观察点 / 单步这类「停一下不该收工」的停点跳过，连续跳过 64 次兜底收工。④ 断点命中：内核 Halted 只带 pc ⇒ 服务端用 ListBreakpoints 的权威表按 pc 找回 {id, addr, kind}（不猜、不另造停因）。⑤ 观察点：契约没有 List 命令（Set / Clear 的回执只有 Tick）⇒ 宿主新增只读访问器 list_watchpoints；POST 缺省 id = 现有最大 + 1，显式给 id 则覆盖（内核语义）。⑥ 事件帧改用 M-07 帧（{type:event, seq, sessionId, role, reqId, payload}），payload 是完整的契约 Message（{schema_version, direction, seq, payload}；v1.10 订正：v1.9 只发内层 {"Event":…}，前端 decodeMessage 第一步读 schema_version ⇒ 整帧 E_PROTO-08）；不带 crc —— 需求口径只列五个字段，前端解码对「没有 crc」放行。⑦ console 推送：WS 每拍顺带推 console 增量（payload = EventPayload::Console，seq = console 绝对偏移）⇒ 与 GET …/console?offset= 同一份账；窗口丢失推 resume{lost, base} 而不是静默少字节。⑧ 「忙」的一瞬假阳性：会话线程先发回执再清忙位 ⇒ submit 加 3 ms 宽限；真在跑的命令照样 409（口径没放宽）—— /api/boot 连续调用踩到过这个缝。
R-12 / R-13 的收口口径（v1.9）：① 判定通道只剩一条：tools/boot-osz.sh 只走 POST /api/boot；crates/kernel/src/bin/osz-boot.rs 已改成该端点的客户端（它自己不再 KernelHost::new()、不再按镜像地址自动选档）⇒ ⇒ 板、停因、预算、墙钟都由服务端判，离线 runner 从此不存在；CLI 名字、stdout=原始字节、stderr=判决行、退出码（0/1/2/3）照旧。② 参考侧的内存图不再由客户端挑段：/api/boot 回执新增 x-boot-ram-window（base:size，十进制），取值走契约层 PlatformDescription::ram_window()（「取哪段 RAM」的唯一落点）⇒ osz-boot --print-memory 只是把它打出来，脚本照旧用它拼 Spike 的 -m（SPIKE_MEM 覆盖口仍在）。③ osz-boot 的 --max-console 删除：console 环上限是服务端启动参数，客户端再设一个是第二个真相；墙钟默认改成 5 000 ms（与服务端缺省 --max-run-ms 对齐），脚本起手先读 /healthz.max_run_ms，超了先说清楚而不是等 400。④ 前端 server-mode 接通：mountTransport({mode:'websocket', serverUrl, sessionId}) 由 serverEventsUrl() 推出 ws://…/api/sessions/{id}/events/ws；帧解包仍是 front/lib/frame.js 那一个 decodeFrame ⇒ ⇒ decodeFrame 放行 FRAME_TYPE.Resume（此前只放行 command/event ⇒ ⇒ 服务端的 resume 会被当畸形帧丢掉，正是 R-13 禁止的「静默断流」）；resume 帧进状态 lastResume（丢帧、console 丢窗口、通道关闭三种都说成人话）并照常交给订阅者。⑤ server-mode 是事件通道、不是命令通道：该 socket 只往外推 ⇒ sendCommand 在 server-mode 直接报 E_TRX-03（命令走 REST），不做「发出去没人看」的静默失败。（v1.11 起作废）：命令另开契约命令端点，见下方 v1.11 note —— 事件通道仍然只往外推，这一点没变。
浏览器入口与帧信封（v1.10）：① 帧信封订正：v1.9 的 payload 只发内层 {"Event":…}，而前端 decodeMessage 第一件事就是读 schema_version ⇒ ⇒ 每一帧都落成 E_PROTO-08：页面显示「已连接」，但寄存器 / 终端一个字也没有。这个缺陷躲过了 v1.9 的 Node 冒烟（它只断言「帧类型 + 内层键」）⇒ ⇒ 真 Chrome 一开就暴露（假绿）；现在 EventRing::since 与 console_frame 都发完整信封，判据也改成按前端解码器写（schema_version / direction / 内层 Event 三层都断言）。② CORS 闸门：页面与服务端天然是两个 origin（front/ 由任意静态服务器托管）⇒ ⇒ 不起这一层，浏览器在跨域检查那一关就拒。放行集合 = 显式 --cors-origins ∪ 回环 origin（{http,https}://{127.0.0.1,localhost,[::1]}[:port]，任意端口）；不接受通配 *（等于把内核的执行能力交给任何网页）；预检 OPTIONS 在中间件里直接 204（不进 require_token），并把 x-boot-* / x-console-* 列进 Access-Control-Expose-Headers —— 不 expose 的话浏览器读不到这些头，会以为「服务端没给」。③ 页面入口：?server=&session=&token=&board=（不给 server 就仍是本地 Worker 模式，一个字都不改）。server 收 http(s)://host:port / ws(s):// / 裸 host:port；给了会话先 GET /api/sessions/{id} 验活（404 才重建，500 / 连不上原样抛、不偷偷建），没给就 POST /api/sessions；然后把会话绑给 M-07、GET …/state 取一次 pc / 寄存器 / t_ps 翻成 SimStateDelta + Tick 两条事件推进视图。服务端模式下不跑 loadProjectIntoKernel 与 Nop 往返（那是本地内核的命令面，服务端会话早有自己的镜像）。④ 范围：本轮接通的是观察面（事件流 + console 推送 + 状态水合）；界面上「运行 / 单步 / 断点」等按钮仍走 M-05 → M-07 的写通道，在 server-mode 会显式报 E_TRX-03（命令走 REST）—— 不伪装成能用。
契约命令端点：页面在 server-mode 也能下令（v1.11）：① 为什么不是映射表：把 M-05 的 dispatch 逐条翻译成 REST 端点（run / step / reset / 断点 / 读内存 …）至少要写二十来条映射，每条还要做字段形状转换 —— 那是第二份真相。内核的入口本来就是 host.handle_message(&Message) -> Vec<EventPayload> ⇒ ⇒ 让它直接吃前端发的那条契约消息，一张表都不用。② 端点形状：POST /api/sessions/{id}/command，体 {message: <完整契约 Message>, reqId?: number}，回 {frames: [ <M-07 事件帧> ]}。方向必须是 Command（否则 400，别让「事件上送」静默变成一条命令）。③ 执行体只有一个：新作业 Job::Contract 投进现有会话线程与唯一的作业队列，执行 host.handle_message ⇒ ⇒ 与 REST 的 Job::Debug 共用同一条执行路径，不存在第二套；内核的业务错误（E_PLT-22 / E_DBG-02 …）不转 HTTP 错误，仍以 Error 事件当应答 ⇒ ⇒ 一个判据只有一个落点。④ 应答与推事件分开：约定与 Worker 通道逐字相同（front/kernel-worker.js："the first event answers the command … the rest are pushed events"）⇒ 回体只给应答那一帧（带 reqId），它不进事件环；其余事件（状态增量 / console / 波形）照旧进环 ⇒ ⇒ 同一份事件只有一条路到页面（前端不需要去重，「同一条增量算两遍」不可能发生），而观察端仍然看得见运行现场。应答帧的 seq 取自保留号段（2^40 起）⇒ 一眼能看出「它不是事件流里的那一条」，也不会与环的 seq 撞号。⑤ 前端只换一个实现：m07_transport 的 server-mode 适配器把 send 从抛 E_TRX-03 改成 POST 契约端点，回体帧喂同一条 emitFrame ⇒ ⇒ M-05 的 dispatchCommand / handleFrame / 500 ms 超时 / Error 分派一行未动。POST 失败时合成一条带同一个 reqId 的 Error 帧（不回帧就等于让命令白等 500 ms 再报超时，把真因藏起来）；只给了裸 url（没有 REST 基址）时仍明确报 E_TRX-03。⑥ 订阅归属：契约路径不代订任何 topic —— LoadProject 会清空内核订阅，页面自己按本地模式的习惯重订（contract_load_project_leaves_resubscription_to_the_client 就是这条判据）；REST 装载路径的「代订 sim.state.delta」只服务不认识契约的客户端。⑦ 证据：服务端 56 项（+5：解码形状 / Tick 应答号段 / 应答不进流 / 契约装载不代订 / 方向闸门）、前端 828 项（+9：地址、请求体、错误体、回体校验、适配器接线）；真 Chrome 点两次「单步」⇒ 页面 x5 0 → 2、pc 0 → 8，同时服务端 GET …/state 的 executed 0 → 2 —— 驱动的是原生内核，且计数没有翻倍。
一个端口与容器部署（v1.12）：① 为什么要有 --front-dir：页面与 API 天然是两个 origin ⇒ ⇒ 用户得另起一个静态服务器，还要靠 CORS 放行（换主机名就再配一次）。给了 --front-dir，同一个端口既回页面又回 API ⇒ ⇒ 同源请求根本不走跨域检查，第二个进程与 CORS 白名单一起消失。② 静态层的三条硬约束：不遮蔽 API（兜底先判 /api… 与 /healthz，再让位于文件）；不出根（路径按段规范化，拒 ..、拒反斜杠、拒任何 %，解析后还要 canonicalize 并确认仍在根内 —— 软链接也不行）；不许陈旧（一律 no-store：前端是零构建的 ES module，缓存旧模块的后果是「改了没生效」甚至整页空白）。启动期就把 --front-dir 规范化并检查 index.html ⇒ ⇒ 打错目录在启动时失败，而不是起好了、浏览器一开却 404。③ 页面不再需要 ?server=：前端发一次同源 GET /api/version，真回了 kernel + schema_version 才进 server-mode（随便一个 200 的网页不算）；探测失败/超时/形状不对 ⇒ 回本地 Worker 模式，不抛（降级不许被写成故障）。④ R-15 的唯一例外：浏览器的 WebSocket 构造函数不能带自定义请求头 ⇒ ⇒ 一旦开了 --token（容器部署必然开），事件流就永远 401 —— 表现为「命令能下、现场不动」。所以令牌判据改成：头优先，且只对 …/events/ws 的升级请求放行 ?token=（解开 %XX 后再比）；REST 仍然只认 x-auth-token。这条是对浏览器限制的让步，不是「令牌可以随便进 URL」的许可 ⇒ ⇒ 令牌会出现在访问日志里，反代侧要脱敏。⑤ 容器：多阶段构建（rust:1-bookworm → debian:bookworm-slim），运行层 非 root（uid 10001）、只装 ca-certificates 与 curl（后者只给 HEALTHCHECK /healthz 用）、/data 挂卷当镜像白名单根；compose.yml 给默认板 qemu-virt（否则会话建出来是「无板」，装载会被 E_PLT-22 拒）；deploy.sh 生成随机令牌（权限 600）、起容器、轮询健康状态、打印带令牌的地址。⑥ 证据与未验证项：服务端 70 项（+12：静态解析/穿越/类型/缓存头/HEAD/写拒 + 令牌判据 + 查询串解码）、前端 838 项（+10：同源探测 6 + 事件流令牌 4）；真 Chrome 冒烟（一个端口 + 令牌，地址里没有 ?server=）：状态栏 已连接 · server websocket、点两次「单步」⇒ x5 0 → 2 / pc 0 → 8、服务端 executed 0 → 2、无 console 报错。⚠️ 镜像本身没有实跑：本轮开发机上没有 Docker 引擎 ⇒ ⇒ Dockerfile / compose.yml / deploy.sh 只做了静态校验（脚本 bash -n / sh -n、compose YAML 解析、路径与参数逐项对照服务端 --help），docker build 与容器内启动尚未验证 —— 这一点如实登记，别当成已验证。
读接口的语义要点：state 返回 {pc, gpr[32], t_ps} —— pc 单独一个字段，不在 gpr 里，且 gpr[0] 恒 0（需求里踩过的坑就在这）；memory 的 len ≤ 4096（契约 DUMP_MAX_BYTES），越界原样拒；format=u32|asc 只追加视图（原始字节仍在 bytes 里，两个消费者不必二选一）；symbols 精确命中与候选并存（候选上限 16）；disasm 允许短于 count（未映射即止，与内核一致）。

5 处理流程

5.1 会话建立与配板

建会话是一个串行化的装配：配额 → 线程 → 板 → 注册。任一步失败都要把已经拿到的资源还回去（线程 join + 配额归还），否则「建会话失败」会漏出孤儿线程。

  • 配额检查通过才起线程；线程启动后立刻进入等待态（队列空），不会有「半初始化会话」被别的请求看见。
  • --board 的默认板在建会话时执行一次 PutBoard，并在会话元数据记 board_source="startup-default"；客户端自己配的记 "client"。
  • 模板来源走 GetPlatformTemplate 取整份描述再 SetMemoryMap —— 与前端同一条路径，不另抄模板数据。
  • 装配失败一律不注册；POST /api/sessions 返回错误体，客户端拿到的是 404/409，而不是一个「建好了但没板」的会话。

5.2 运行：分段推进与停因

「跑到什么时候停」由服务端判定，客户端不再切 StepN。一个窗口 = 一次 Continue（量子 10 000 条）；每个窗口结束做四件事：取 console、记账、判停因、查 deadline。

// run_window 的核心循环（伪码，逐字对应表 13 的判定次序）
fn run_window(host, spec, deadline, ctrl) -> StopReport {
    let before = host.total_executed();
    let mut windows = 0u64;
    loop {
        // ① 内核先跑一个量子窗口（不在服务端切更小的片）
        let ev = host.handle_message(&Message::command(seq, Continue));
        let halted = ev.iter().find_map(|e| as_halted(e));       // HaltReason

        // ② 先记账：console 进 ring，事件进 fanout（响应之前必须可读）
        ring.append(&host.drain_console());   // 取走本窗口产生的字节
        windows += 1;

        // ③ 再判停因（纯函数，固定次序）
        let obs = Obs { halted, ctrl, deadline, ring, spec,
                        executed: host.total_executed() };
        if let Some(reason) = judge_stop(&obs) {
            return StopReport::new(reason, host.total_executed() - before,
                                   host.pc(), host.now_ps(), ring);
        }
        if let Err(err) = first_kernel_error(&ev) { return StopReport::failed(err); }
    }
}

5.3 console 的一致性

console 是字节不是字符串：ANSI 序列、\r、半截 UTF-8 一律不加工。ring 用绝对 offset，只追加、不改写；裁剪只从尾部发生，并在丢弃表里留证据。

// append：只追加，裁剪时记账（不静默丢）
fn append(&mut self, bytes: &[u8]) -> Range<u64> {
    let from = self.total;
    self.buf.extend_from_slice(bytes);
    self.total += bytes.len() as u64;
    while self.buf.len() > self.max {
        let cut = self.buf.len() - self.max;
        self.buf.drain(..cut);              // 只从头部裁
        let dropped_from = self.base;
        self.base += cut as u64;
        self.dropped.push((dropped_from, self.base));
    }
    from..self.total
}

// read：三种结果必须可区分，不许都变成「空」
fn read(&self, off: u64, limit: usize) -> ReadResult {
    if off < self.base {
        return ReadResult::Lost { base: self.base, dropped: self.dropped.clone() };
    }
    if off > self.total { return ReadResult::Future { total: self.total }; }
    let start = (off - self.base) as usize;
    let end = (start + limit).min(self.buf.len());
    ReadResult::Bytes { bytes: self.buf[start..end].to_vec(), total: self.total }
}

5.5 并发、隔离与复位

6.2 边界与降级

  • 装载失败不改变机器状态：与内核次序纪律一致 —— 解析、门禁、建图都在写入之前完成，失败时寄存器与内存一个字节不动。
  • 配板 pending 不自动重载：换了板但没重装镜像时，返回 pending:true；不替客户端做「顺手重装载」，否则故障现场被抹掉。
  • 超时后再 run：允许；reset 也只是重发一次 LoadProject，语义与前端「复位」同口径。
  • WS 断流：连接断即退订；不保留「断线期间的事件」缓冲（P1 只保证 console 可从 REST 补齐）。
  • 请求体过大：413 + E_PROTO-08（tower_http::limit，默认 32 MiB）+ E_PROTO-08；不给解析器制造 OOM 的机会。
  • token 缺失（远程模式）：401 + E_SESS-07，detail 只说「需要 X-Auth-Token」，不回显期望值。
