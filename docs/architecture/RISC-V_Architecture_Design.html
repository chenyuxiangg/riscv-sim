  • 总体架构：五横层——① 前端交互层（多视图独立路由，FR-23）② 会话/命令层（会话隔离、快照持久化，FR-13/19）③ 调试服务层（断点/单步/反汇编·源码联动/寄存器内存/波形/trace，FR-05/08/09/10/14）④ 仿真内核层（事件驱动引擎 + ISS + 分级外设 + 总线映射，FR-01~04/06/07）⑤ 观测管道层（探针 + 边沿编码 + 增量推送，FR-10）；另有横切基础设施——日志系统（记录，仅系统管理员通道）与健康管理 HMS（监测/分级/分角色分发/降级，NFR-07/08）；按角色装配三工作台（产品/嵌入式/系统管理员，§3.4）。

  • 数据模型：Project(产品树) / SimState / DebugMeta / Waveform / ProtocolMessage 五类核心模型 + P1 预留 Interconnect Link（多板互联数据面），为前后端、双形态、双内核的公共契约。
  • 架构决策（ADR）：事件驱动时序、分级外设、解释执行+双内核、双源探针、three.js(P1)、前端承载零构建改义（评审 R2/R7）——全部有候选与权衡（第 9 章）。

CHAPTER 2

架构设计概述

架构设计目标 / 架构设计约束 / 架构设计原则 / 架构设计方法

架构设计目标以「可观测性 × 易用性 × 合规 × 可扩展」为第一优先级，保真度以「够用」为界——差异化不拼「仿得更真」而拼「看得更清、上手更快」。所有目标、约束、原则均由需求推导并有据可查。

2.1 架构设计目标

G1 可观测性优先

波形、单步、反汇编·源码联动、内存/寄存器、trace 是差异化核心（需求 1.4 硬能力 2）。架构让每个可观测动作有确定归属、低延迟、可增量推送。观测管道（第 8 章）为独立横层。

G2 零安装与易用

浏览器 WASM 或服务端 WebSocket，同源 HTTP 部署直接可开（NFR-05）。内核可内嵌或远程承载，两形态共用同一协议与数据模型（第 6 章物理架构）。

G3 内核与前端解耦、双形态

仿真内核与前端解耦（NFR-06）。ExecutionBackend 使同一套调试服务与前端可对接 WASM 自研 ISS 或服务端 QEMU（决策点 3）。

G4 确定性可复现

测试者核心价值（FR-12，借鉴 Simics 检查点）。架构把虚拟时间推进、事件调度、随机源收敛到确定性引擎，固定种子即复现，为快照/回放预留。确定性范围 = 种子 + 时间戳化输入事件序列 → 结果唯一（§8.1 D0，评审 R8）。

G5 合规与安全

GPL 合规（R2）、WASM 沙箱 + XSS 防护（NFR-04/R6）。内核可自研（BSD/MIT）并支持进程隔离，前端字符串统一转义，固件仅沙箱内执行。

G6 可扩展（插件化）

外设分级建模（NFR-06，借鉴 Spike 共享库/Renode 分级）。Peripheral 抽象 + 注册表 + 实例化到地址区间，支撑 UART/GPIO/定时器起步，LCD framebuffer 与更多外设随 P1 插件化加入。

运行架构设计

进程/线程与并发模型 / 核心运行机制（量子化混合调度）/ 关键时序 / 双内核运行策略

运行架构以「量子化混合调度」为核心运行机制（对应 4+1 的运行视图），实现事件驱动时序（决策点1）与确定性可复现（FR-12）；并以「Worker 内核切片（主路径）+ 分片降级兜底 + 服务端会话隔离」的并发模型支撑双形态与并发目标。

5.1 进程 / 线程与并发模型

浏览器 · 无 Worker 环境降级（兜底，评审 A）

主路径为 Worker（下卡，韧性基线）；仅在 Worker 不可用的环境（如受限的旧浏览器）降级为「仿真与 UI 同一主线程按时间片交替」（requestIdleCallback/分片，切片预算：每 ≤10⁴ 条指令或每 10–50ms 宿主时间检查一次命令队列并让出，保证命令响应 ≤500ms 有最坏情况边界），避免阻塞 UI（NFR-02）；降级路径不承诺 guest 失控隔离（watchdog 超时只能抛事件，无法 terminate）。

浏览器 · Worker（MVP 韧性基线）

仿真内核（ISS/引擎/外设/观测）默认移入 Web Worker，postMessage 承载协议消息，主线程专职 UI 与渲染；主线程 watchdog 定时器周期性确认 Worker 心跳，超时（如 guest 死循环占死内核）即 terminate Worker 并抛「guest 失控」超时事件交由 HMS 处置（评审 R3）。Worker 以同源 URL 创建（HTTP 部署；P1 可评估 blob URL 内联，不破坏零安装属性）（ADR-6）。

服务端 · 会话隔离

每会话一个 ExecutionBackend 实例（进程/线程池），状态完全隔离；≥10 并发会话稳定（NFR-03，V-09）。每会话配额：内存上限（默认 256MB）与 CPU 时间片预算；会话数准入上限（默认 ≥10）+ 超限拒绝新会话并告警（评审 R11）。

确定性不受并发影响

同一会话内虚拟时间推进独立于宿主调度；多会话互不共享确定性种子与事件序列。

5.2 核心运行机制：量子化混合调度

事件驱动（决策点 1，借鉴 Renode 时间框架）与确定性（FR-12）在「时间量子」处统一。设计不采用纯事件驱动（每事件处理完 CPU 空闲）也不采用纯周期精确，而是「时间驱动 + 事件分发」的混合：主循环以 1µs 时间量子为 IRQ 采样节奏，每量子先处理到期事件、再让 ISS 执行指令；无到期事件时批量推进到下一事件/检查点（不逐量子空转）。访存同步分发、中断在量子边界采样。每量子固定开销（事件检查 + IRQ 采样 + 控制注入检查）预算 ≤ 单量子指令执行时间的 10%【估算基线，实现后实测校准】；5 MIPS 下 1µs 量子 ≈5 条指令，批量推进保证开销占比不随空转放大。

已知延迟声明（评审 L2）：1µs 量子 IRQ 采样意味着虚拟中断响应延迟 ≤1µs（采样边界对齐），这是架构级已知延迟而非模型错误；驱动调试时序敏感代码（如临界区/关中断窗口）时应以此校准预期。

指令预算 watchdog（评审 R3）：内核每执行 ≤10⁴ 条指令检查一次宿主时间预算，单片超时（宿主阈值可配，默认 200ms）即判定「guest 失控」并抛超时事件——与 M1 切片预算共用同一检查点（指令计数边界），在 Worker 线程内执行，不占死主线程；guest trap（访存异常/非法指令）由内核捕获为 guest 异常，属模型内事件，与本 watchdog 的平台级超时严格区分（§8.5/§10.7 故障分类）。

量子化混合调度主循环（运行视图示意）。确定性由固定种子 PRNG + 稳定事件排序保证；无事件时批量推进到下一事件/检查点（量子仅作 IRQ 采样节奏）；控制注入只在安全检查点（事件边界 ∨ 指令计数边界）发生，避免半指令状态。

5.3 关键时序设计

关键时序（运行视图示意）：量子化推进虚拟时间；观测推送按批节流、独立于仿真节奏；控制命令只在安全检查点（事件边界 ∨ 指令计数边界）注入。

5.4 双内核运行策略（决策点 3 + R1/R2）

双形态 × 双内核（运行视图示意）。浏览器 WASM 满足 MVP 零安装；服务端形态承载长任务与 QEMU 双内核，经 ExecutionBackend 统一接口接入，能力面按分级协商（QEMU=L1 子集，指令钩子/快照仅自研 ISS）。GPL 合规（R2）在服务端用进程隔离、浏览器端用自研 BSD/MIT 内核。

虚拟时间锚点

所有流携带虚拟时间戳（非宿主时钟），跨流可逐事件对表（日志↔trace↔波形同轴，§8.1）。

会话隔离

数据不跨会话串扰：独立种子/事件序列/日志缓冲；并发会话（NFR-03）各自成流。

角色可见性边界

产品/嵌入式只收 S1/W1/T1/E1 + HMS 可读提示；系统日志仅系统管理员（§3.4）。

背压与节流

上行流环形缓冲 + 边沿压缩 + 批量节流；下行流请求时限；波形采样可配降载。

失败语义

命令超时可重试（幂等）；断线按序列号续拉；写失败降级 + 告警，不静默丢失关键状态。

双形态同一性

WASM 内嵌 / WS 远程走同一协议与数据流；传输适配层（M-07）切换不影响上层（§6）。

快照一致性

快照以量子边界为检查点，与证据流记录对齐；崩溃恢复 = 最近检查点 + 输入序列重放（评审 R1，§10.2）。

数据版本

协议与持久化 schema 带版本；不兼容 → 明确拒绝并提示升级路径，不静默错读（§11.2）。

8.1 确定性机制（FR-12 / NFR-07）

D1 固定随机种子

外设随机源（噪声、按键去抖抖动、ADC 采样等）统一来自种子化 PRNG；同种子 → 同随机序列。

D0 确定性范围定义（评审 R8）

确定性 = 给定种子 + 时间戳化输入事件序列（含注入时刻）→ 结果序列唯一；宿主相关因素（命令到达时机、UI 交互节奏、断点命中后的观测时机、宿主时钟）不在承诺范围，不保证跨宿主/跨会话复现观测时序。

D2 稳定事件排序

事件队列按（虚拟时间, 插入序）稳定排序，同刻事件以注册顺序确定处理，消除宿主线程/时钟抖动影响。

D3 虚拟时间独立

虚拟时间仅由量子推进，不依赖宿主 Date/时钟；仿真速率（MIPS）只影响快慢，不影响结果序列。

D4 事件流记录（证据流，评审 R1）

会话层记录证据流（FR-12 预留），为回放/快照（FR-19）与测试者缺陷复现提供证据。外部输入（UART 写、按键、GPIO 注入）统一时间戳化、经事件队列入事件流（评审 M6）——输入捕获闭环是 D4 成立的先决条件。证据流是稀疏输入事件序列（每次注入一条、频率低），容量可行；恢复路径 = 检查点 + 该输入序列重放执行，不依赖全量波形/trace 证据流（评审 R1）。

8.2 观测管道（差异化核心）

波形是竞品普遍空白（需求 2.5）、本平台差异化核心。观测管道把它做成「性能可控的异步流」：探针边沿编码压缩、环形缓冲 + 增量推送控制带宽、采样率可配。观测只读、不改仿真状态，与内核解耦。

双源探针（决策点 4）

总线级 trace（底）

监听地址读写事件流（每访存记时间戳 + 地址 + 方向 + 宽度），覆盖全部访存，语义少、噪声大——作事件流底与访存 trace（FR-14）。

外设级探针（面）

外设模型内埋点暴露语义丰富信号：GPIO 翻转、定时器比较、中断脉冲、按键状态——作波形通道。Peripheral 通过 probe(signal,value,time) 上报。

CHAPTER 9

架构决策（ADR）与技术选型

六大架构决策记录 / 逐模块技术选型矩阵 / 关键选型决策依据

六大架构决策（ADR）均对齐「够用保真度 × 极致易用 × 可观测 × 合规」目标，全部有候选与权衡，不默认最优、不拍脑袋。选型以 ADR 为纲、以矩阵为表，落实到各模块。

9.1 ADR-1 · 时序精度：事件驱动

问题：仿真时间如何推进，决定「虚拟时间 → 真实时间」映射精度与实现成本。
选项：A 事件驱动（时间量子/事件队列）；B 周期精确；C 混合（行为级 + 可选 RTL 协同）。
权衡：事件驱动快、模型成本低，足以功能验证与驱动开发；周期精确保真度高但慢、建模贵——商用三巨头均把周期精确让位给 RTL 仿真/emulation（Synopsys ZeBu/HAPS、Simics 功能验证、Imperas 指令精确）。
决策：MVP 采用事件驱动，时间量子 1µs 级（借鉴 Renode）；预留 Verilator HDL 协同接口。

9.2 ADR-2 · 外设建模粒度：分级建模

问题：外设模型精度层级，决定驱动兼容性与调试视图价值。
选项：A 寄存器级；B 行为级；C 分级体系（标签→脚本→行为模型→HDL 协同）。
权衡：寄存器级利于驱动兼容（QEMU）但成本高；行为级快但可能误导时序敏感驱动（Wokwi 明示模拟支持有限）。
决策：分级建模（Renode 四级蓝本）；MVP 取「寄存器接口 + 行为级时序」——UART/GPIO/定时器首批寄存器级，其余按需分级。

9.3 ADR-3 · 仿真性能：解释执行 + 双内核

问题：内核执行引擎，决定浏览器内可用性能上限与实现复杂度。
选项：A 纯解释（WASM 可移植、逐指令可观测）；B JIT/二进制翻译（TCG 式）；C 混合（解释 MVP + 后期 JIT/服务端双内核）。
权衡：解释简单、可观测好（Spike 40–240 MIPS 广泛用于验证教学）；JIT 快（QEMU TCG 100M–1B 指令/s）但实现复杂、WASM 下更难；Wokwi 证明浏览器内解释可产品化（~8MHz 限速）。
决策：MVP 解释执行（WASM），目标 5–10 MIPS；架构预留 JIT（解码-翻译-执行流水线）；服务端可选 QEMU 双内核跑长任务/整机——经 ExecutionBackend 隔离（合规 R2）。

9.4 ADR-4 · 波形来源：双源探针

问题：波形数据从哪里采样，决定波形语义丰富度与实现成本。
选项：A 总线探针；B 外设内部信号；C 混合。
权衡：总线探针实现简单、覆盖全部访存但语义少、噪声大；外设内部信号语义丰富但需每个外设埋点。
决策：混合——总线级 trace 为底（事件流，借鉴 QEMU TCG 插件）+ 外设级探针为面（波形通道，借鉴 Renode LogPeripheralAccess）。波形是普遍空白、差异化机会。

9.5 ADR-5 · 3D 可视化引擎（P1）

问题：产品→主板→元器件三层 3D 交互视图（旋转/缩放/点选下钻）用何种前端技术实现。
选项：A three.js（WebGL，浏览器原生、生态成熟）；B WebGPU 原生；C 2D 增强。
权衡：three.js 与 Web 零安装一致、社区成熟，但引入 WebGL 渲染线程与仿真线程耦合复杂度（R9）；2D 增强成本低但失去「3D 原型构建 + 调试联动」差异化。
决策：列 P1（不进 MVP）；MVP 以 2D/树形闭环；P1 里程碑 MVP → 2D 增强 → three.js 3D 下钻（FR-21）→ 帧缓冲渲染（FR-22）。产品树同源（不另造数据模型）。

9.6 ADR-6 · 前端承载：零构建 vs 零依赖（评审 M3/L4）

问题：两个独立命题——「零构建」（无打包步骤）与「零依赖」（无外部网络依赖）——此前混为一谈；目录形态下 WASM 与 P1 three.js 如何承载需明确。
选项：A 原生 JS + 全部内联（零构建、零依赖、单文件）；B 构建产物单 HTML（零依赖、有构建步骤）；C 原生 JS + 关键依赖 CDN（零构建、有网络依赖）。
权衡：同源 HTTP 部署的真正约束是 ES module CORS 与外部资源不可达（与框架无关）；three.js 走 CDN 则离线失效，与「零依赖」冲突；WASM 内联 base64 会膨胀文件（内核 1–3MB → base64 增约 33%）且首屏加载变慢——故目录形态下不内联 WASM，直接以同源静态资源加载。
决策：MVP = 方案 A——原生 JS 零构建 + WASM 内联 base64（目录形态 + 同源 HTTP 部署为最终形态（用户决策 2026-10-20；NFR-05 相应修订，单文件自包含降级为可选交付形态，不再作为 MVP 硬指标）；目录形态下由同源静态服务器承载：入口 index.html + 相对 import 的模块图 + wasm 文件）；P1 3D = 方案 C 的受控变体：three.js 走可信 CDN，离线环境 3D 视图降级为 2D/树形（能力协商降级，§11.2），不阻塞核心闭环。「零构建」= 零安装交付属性（用户侧无需任何构建步骤），非开发期约束：内核由 C/Rust→WASM 经 emscripten/LLVM 编译，开发期构建链与测试工具链（node/jest/CI 对拍）正常存在且不受零构建约束（评审 R2/R7/R12）；零依赖在 MVP 保持、P1 允许 CDN + 降级；波形真图（v0.51 批 · STAGE-36）= 方案 C 的又一处受控变体：波形视图用 echarts 画真图，走可信 CDN（jsdelivr ESM，锁 5.5.1），刻意不 vendor 进仓（vendor 会让「离线不可用」这个已知缺口消失 ⇒ ⇒ 降级路径变成装饰）；离线 / CDN 不可达时波形视图降级为「波形库不可用」提示，通道列表仍在、核心调试闭环不受影响（能力协商降级，§11.2），零构建仍然成立（浏览器原生动态 import()）。

9.8 关键选型决策依据

为何自研 ISS 而非 QEMU

合规是第一硬约束（R2）：QEMU/Unicorn 为 GPL-2.0，浏览器内嵌会触发衍生作品传染，与「开放免费入口」冲突。自研 BSD/MIT 内核（借鉴 Spike/TinyEMU）同时获得指令级可观测（ADR-3），是「可观测 × 合规 × 成本」最优。

为何前端原生 JS

零安装（NFR-05）与同源 HTTP 部署直接可开（V-10）是硬指标，任何构建链依赖（React/Vue 需打包）都会破坏。原生 JS + hash 路由 + 命令驱动重渲染，以略多样板换取零依赖、可审计、零安装——即 Wokwi 路线。

为何波形自研

波形是竞品普遍空白（需求 2.5）、本平台差异化核心。QEMU 需 TCG 插件自建、Renode 是 VCD 导出、Wokwi 是 Logic Analyzer，无一提供运行时内嵌波形面板。自研边沿编码管道是不可外包的护城河（FR-10）。

为何 3D 用 three.js（P1）

three.js 与零安装一致、生态成熟、WebGL 原生（ADR-5）；WebGPU 新且与仿真线程耦合复杂度更高（R9）。列 P1 且产品树同源（FR-21）。
