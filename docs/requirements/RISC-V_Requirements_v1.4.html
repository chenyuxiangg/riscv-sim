执行摘要（一屏结论）

  • 平台定位：无硬件的一站式嵌入式产品原型验证平台，面向嵌入式软件开发者/测试者；三大硬能力 = 多层可视化原型构建（MVP 采用 2D 产品树/原理图，P1 升级可交互 3D 模型）+ 调试可视化（波形 / 软件单步 / 内存查看 / 反汇编·源码联动）+ 以 Web 为前端访问服务（多视图独立路由）；P1 扩展多板互联调试（多板实例与拓扑、板间外设互联绑定、跨板联合调试）。
  • 市场空白判断：四要素组合无直接对标；「多层产品树」与「内嵌波形调试」是两个真实空白点；Web 端「3D 原型构建 + 调试联动」组合同样无人提供（P1 迭代方向）；Web 端「多板互联可视化调试」亦无竞品提供（P1 迭代方向）。
  • 差异化策略：不拼「全 ISA 保真度 + 全外设生态」（那是商用平台的定价根基），拼 Web 原生体验、多层可视化（MVP 2D/树形 → P1 3D 交互）、反汇编/源码联动、多视图分离、多板互联可视化调试（P1）与低门槛免费入口（依据：Imperas/Synopsys/Simics 三家共同空白）。
  • 技术决策：事件驱动时序 + 分级外设建模 + 解释执行（预留 JIT/双内核）+ 总线/外设双源探针波形。
  • MVP 建议：RISC-V ISS(RV32) + UART/GPIO/定时器 + 内存映射 + 2D/树形多层原型 + 单步/断点 + 内存查看 + 反汇编·源码联动 + 简易波形 + 多视图 Web 前端（WebSocket + WASM）；3D 交互视图、屏幕 GUI 帧缓冲渲染、多板互联明确列入 P1，不进 MVP（理由见 6.4）。
  • 关键风险：性能-可观测性权衡（浏览器内解释执行，参考 Wokwi 约 8 MHz 限速仍可产品化）、GPL 合规（若复用 QEMU/Unicorn）、波形数据量、竞品免费化威胁（Wokwi 免费档 / Intel Simics 公开免费版）、3D 渲染与集成复杂度（P1 期）、多板互联复杂度（跨板时钟/事件同步与消息路由，P1 期）。
CHAPTER 1

平台定位与目标

愿景 / 目标用户 / 三大硬能力 / 与竞品的差异化定位

结论先行：本平台的差异化不在「仿得更真」，而在「看得更清、上手更快」。 把商用虚拟平台（Imperas/Synopsys/Simics）用 CLI 与重型 IDE 才做到的整机仿真与调试观测，变成浏览器里可搭建、可下钻、可评审的多层可视化体验；把 Wokwi 的零安装易用性，与 QEMU/Renode 的整机级仿真能力在 RISC-V 垂直场景合流。v1.2 升级方向：多层原型以 2D/树形在 MVP 快速闭环（评审点 2 + 用户决定），P1 升级「3D 可交互原型 + 屏幕 GUI 帧缓冲渲染 + 反汇编/源码联动 + 多视图独立路由」，并新增「多板互联调试」（评审补充：多板实例与拓扑、板间外设互联绑定、跨板联合调试，列 P1）。

1.1 愿景

让嵌入式软件开发者与测试者无需真实硬件，在浏览器中完成「产品 → 主板 → 元器件」的搭建、固件加载、运行与调试验证，形成可复现、可演示、可回归的产品原型验证闭环。MVP 以 2D 产品树/原理图打通闭环；P1 迭代为可交互 3D 模型（旋转/缩放/点选下钻）与屏幕 GUI 帧缓冲渲染到 3D 屏幕表面（如 LVGL 图形界面），并扩展多板互联调试——多板实例、板间外设互联链路（UART/SPI/I2C/GPIO/CAN/以太网等桥接）与跨板联合调试，使「数字双胞胎」从单板进阶为「多板系统级」。

1.2 通俗类比（评审辅助理解）

数字双胞胎 / 全息手术台

沿用既有类比体系：产品是「病人」，主板是「器官系统」，元器件是「细胞与组织」，波形与内存视图是「生命体征监视器」，单步调试是「手术刀」。平台即嵌入式系统的全息手术台——不改动病人，也能看清每一个状态；P1 的 3D 模型 + 屏幕 GUI 渲染，相当于给手术台加上「立体透视 + 病人面前的实时仪表屏」。

飞行模拟器

不买真机先练飞：在真硬件到手前，把固件开发、测试、缺陷复现、方案演示的每一个动作先在「模拟座舱」里完成；飞行模拟器练的是飞行员，本平台练的是固件。

乐高 vs 精雕模型（建模粒度）

行为级外设像乐高——快、够玩、结构清楚；寄存器级/SPICE 级像精雕模型——真、贵、慢。平台按需提供各级精度并明确标注保真度，让用户按验证目标选颗粒度（依据 Renode 四级建模体系【已查证】）。

1.4 三大硬能力

硬能力 1 · 多层可视化原型构建

产品 → 主板 → 元器件 的多层搭建（如 PSP 产品 → 主板 → 元器件）：MVP 采用 2D 产品树/原理图（可点选下钻、属性编辑，快速闭环）；P1 升级为 可交互 3D 模型（three.js 技术选型示例：产品外壳→主板→元器件 3D 模型，旋转/缩放/点选下钻，点击元器件看端口与连接），结构化「产品树」为两者的数据底座；P1 另支持多板拓扑（多 Board 实例 + 板间互联链路，见硬能力 3）。

硬能力 2 · 调试可视化

波形（探针采样渲染）、软件单步调试（断点/单步/PC 与寄存器）、内存值查看、反汇编 + 对应源代码联动显示区（基于符号表/DWARF 做源码-地址映射，PC 高亮当前行）；以「虚拟仪器面板」形态呈现（借鉴 Proteus 仪器面板产品化标准【已查证】），而非散落功能按钮。

硬能力 3 · Web 前端访问服务

以网页（Web）为前端访问服务：浏览器内 WASM 仿真或服务端仿真 + WebSocket 转发（参照 Renode「引擎在服务端 + 浏览器视图」折中架构【已查证】）；前端采用多视图工作区（独立路由）——产品视图、调试视图、波形视图分别独立呈现、可切换，不挤在单页；P1 增加多板拓扑视图（可视化板间连接，点选链路查看两端外设与实时数据流，见 FR-24/25/27）。零安装、即点即用。

2.5 横向洞察（结论先行）

市场空白 四要素组合无竞品 + Web 端「3D 原型构建+调试联动」与「多板互联可视化调试」空白（P1 方向）

「RISC-V 整机级仿真 + Web 原生可视化 + 产品→主板→元器件多层原型 + 面向个人开发者的低门槛免费入口」四要素：Renode 最接近（serveVisualization 浏览器 2D 板卡视图）但无产品树、入口为桌面脚本（其 VSD 3D 渲染为桌面端引擎产物，非浏览器交互式产品树【已查证·来源#B32,B33】）；Wokwi 是 Web 零安装标杆但外设行为级、无产品树、整机规模受限（多 MCU 单项目不支持）；QEMU 整机最强但无 Web 原生与多层可视化；Proteus 可视化成熟但无 RISC-V；商用三巨头均无 Web 原生与多层原型【已查证】。另：波形能力是普遍空白——QEMU 需 TCG 插件自建、Renode 为 Verilator VCD/trace 导出、Wokwi 为 Logic Analyzer（VCD），无一提供原生内嵌波形面板。v1.1 补充：Web 端「3D 原型构建 + 调试联动」组合仍是空白（作为 P1 迭代方向，不改变上述对比结论）。v1.2 补充：Web 端「多板互联可视化调试」亦无竞品提供——Renode 支持多节点/多 MCU 板间互联与多板拓扑，但无 Web 交互式拓扑视图【已查证·来源#B1,B11,B13】；Wokwi 多 MCU 单项目不支持（需多实例+私有网关）【已查证·来源#B54】；QEMU 多实例互联主要走网络 socket（virtio-net/GEM 网络模型【已查证】）【待查证】；Proteus 层级原理图可放置多 MCU 引脚连线【已查证·来源#B39】、深度【待查证】；Simics 多板卡/分布式/数千虚拟 CPU 全系统最强【已查证·来源#C20,C23,C27,C30】但无 Web 端（均为 P1 方向差异化依据，不改变四要素空白结论）。

可借鉴 六条工程路线

① Renode 四级外设建模（SVD 标签→Python→C#→Verilator RTL 协同）= 元器件库分级蓝本【已查证】；② Renode serveVisualization「服务端引擎 + 浏览器 2D 视图」= Web 架构折中范本【已查证】；③ Wokwi「浏览器内 WASM + 行为级外设 + 逻辑分析仪（VCD 导出）」= 零安装调试可视化最小范式【已查证】；④ Proteus 虚拟仪器面板（示波器/逻辑分析仪/协议分析器）= 调试可视化的产品化标准【已查证】；⑤ Spike「黄金基准 + 极简调试交互（reg/mem/until）」= 指令正确性对拍器【已查证】；⑥ Simics 确定性/检查点/快照 与 OVP「开放 API + 免费入口 + 商业增值」分层 = 测试者场景杀手锏与商业化漏斗【已查证】。

威胁 三个方向

① Wokwi 免费档体验极佳且被 Espressif 官方收录（ESP-IDF 文档第三方工具），其行为级外设 + ESP32-C3 系列 RISC-V 覆盖会侵蚀「教学/快速原型」客群【已查证】；② Renode 开源 + 商业服务且 RISC-V 生态最深（SiFive/GD32/Microchip/OpenTitan），若其 serveVisualization 升级为产品树即直接竞争【已查证】；③ 商用三巨头若推出免费 Web 评估版（Intel Simics 已有公开免费版先例）将形成降维竞争；波形空白可能被快速填补【已查证】。

CHAPTER 5

技术决策点

四个已建立的技术决策点：时序精度 / 外设建模粒度 / 仿真性能 / 波形来源，另附 v1.1 新增的关联决策 5（3D 引擎选型，P1）。每个含：问题 / 选项 / 权衡 / 建议 / 竞品佐证。

结论先行：四组建议共同指向「够用保真度 + 极致易用」——事件驱动、分级建模、解释执行起步、双源探针。 与商用平台的差异不拼全 ISA 保真度（Imperas 宣称「支持全部已批准扩展」为厂商口径【已查证·厂商宣称·来源#C3】），而拼「可观测性 × 易用性 × 成本」的最优组合；四组决策全部有竞品佐证支撑。

决策点 1 · 时序精度：事件驱动 vs 周期精确

问题：仿真时间如何推进，决定「虚拟时间 → 真实时间」的映射精度与实现成本。
选项：A 事件驱动（时间量子/事件队列调度）；B 周期精确（cycle-accurate）；C 混合（行为级 + 可选 RTL 协同）。
权衡：事件驱动快、模型成本低，足以支撑功能验证与驱动开发；周期精确保真度高但慢、建模贵——且商用三巨头均把周期精确让位给 RTL 仿真/emulation（Synopsys ZeBu/HAPS 混合仿真【已查证·来源#C13】；Simics 定位功能验证【已查证·来源#C19】；Imperas 为指令精确而非周期精确【已查证·来源#C6】）。
建议：MVP 采用事件驱动，时间量子 1µs 级（借鉴 Renode 全局时间量子 min 1µs【已查证·来源#B13】）；预留 Verilator HDL 协同接口（借鉴 Renode【已查证·来源#B5】）以满足后期 RTL 级验证需求。
竞品佐证：Renode 时间框架（量子化、确定性优先）【已查证·来源#B13】；Simics 时域解耦【已查证·来源#C20】；Imperas OVP 行为级建模 + 事件调度【已查证·来源#C6】。

决策点 2 · 外设建模粒度：寄存器级 vs 行为级

问题：外设模型的精度层级，直接决定驱动代码兼容性与调试视图价值。
选项：A 寄存器级（精确地址/寄存器语义）；B 行为级（功能正确、时序简化）；C 分级体系（标签→脚本→行为模型→HDL 协同）。
权衡：寄存器级利于驱动兼容与寄存器调试（QEMU 采用【已查证·来源#A1】）但成本高；行为级快但可能误导时序敏感驱动（Wokwi 官方明示「模拟支持非常有限」【已查证·来源#B56】）。
建议：分级建模（Renode 四级蓝本：SVD 标签→Python→C#→Verilator【已查证·来源#B3】）；MVP 取折中「寄存器接口 + 行为级时序」——UART/GPIO/定时器首批以寄存器级实现，其余外设按需分级。
竞品佐证：Renode 分级体系【已查证】；QEMU 寄存器级多板卡【已查证】；Wokwi 行为级 WASM 模型【已查证】；Proteus SPICE 级最细但闭源且无 RISC-V【已查证·来源#B35】。

决策点 3 · 仿真性能：解释执行 vs JIT/二进制翻译

问题：内核执行引擎，决定浏览器内可用的性能上限与实现复杂度。
选项：A 纯解释（WASM 可移植、逐指令可观测）；B JIT/二进制翻译（TCG 式）；C 混合（解释 MVP + 后期 JIT/服务端双内核）。
权衡：解释简单、可观测性好——Spike 解释执行 40–240 MIPS 被广泛用于验证与教学【已查证·来源#A29,A31】；JIT 快——QEMU TCG 100M–1B 指令/s（约 10–30× 减速）【已查证·来源#A14,A22,A23】但实现复杂、WASM 下难度更高；Wokwi 证明浏览器内解释可产品化（默认 ~8 MHz 限速）【已查证·来源#B50】。
建议：MVP 解释执行（WASM），目标 5–20 MIPS 量级【估算】足够 UART/GPIO 级固件测试；架构预留 JIT（参考 Imperas「解码-翻译-执行」流水线【已查证·来源#C6】）；服务端可选 QEMU 双内核跑长任务/整机。
竞品佐证：Spike/QEMU 性能数字【已查证】；Wokwi 限速实践【已查证】；Imperas JIT 1 BIPS（2009 历史数据）【已查证·来源#C7】。

决策点 4 · 波形来源：探针挂总线 vs 挂外设内部信号

问题：波形数据从哪里采样，决定波形语义丰富度与实现成本。
选项：A 总线探针（监听地址读写）；B 外设内部信号（外设模型内埋点）；C 混合。
权衡：总线探针实现简单、覆盖全部访存但信号语义少、噪声大；外设内部信号语义丰富（GPIO 翻转/定时器比较/中断脉冲）但需每个外设埋点。
建议：混合——总线级 trace 为底（事件流，借鉴 QEMU TCG 插件 load/store 回调【已查证·来源#A8】）+ 外设级探针为面（波形通道，借鉴 Renode 外设访问日志 LogPeripheralAccess【已查证·来源#B10】）。波形能力是普遍空白，属差异化机会。
竞品佐证：QEMU TCG 插件【已查证】；Renode Verilator VCD/trace + LogPeripheralAccess【已查证】；Wokwi Logic Analyzer（8 通道 / 1 GHz / VCD 导出）【已查证·来源#B51,B52】。

关联决策 5 · 3D 可视化引擎选型（P1 迭代方向，评审点 2）

问题：产品→主板→元器件 三层 3D 交互视图（旋转/缩放/点选下钻）用何种前端技术实现。
选项：A three.js（WebGL，浏览器原生，生态成熟、选型示例）；B WebGPU 原生；C 2D 增强（仅升级原理图/板卡视图，不引入 3D）。
权衡：three.js 与 Web 零安装目标一致、社区成熟，但引入 WebGL 渲染线程与仿真线程的耦合复杂度（见风险 R9）；2D 增强成本低但失去「3D 原型构建 + 调试联动」的差异化想象空间。3D 与屏幕 GUI 帧缓冲渲染（FR-22）依赖 L1 显示外设 + L3 帧缓冲更新时序 + L5 纹理映射协同，需三处同步迭代。
建议：列 P1（用户决定，不进 MVP）；MVP 以 2D/树形多层原型闭环；P1 里程碑：MVP 闭环 → 2D/树形增强 → three.js 3D 模型与点选下钻（FR-21）→ 屏幕帧缓冲渲染到 3D 表面（FR-22）。报告页面自身零外部依赖，three.js 仅作为产品技术选型写入本需求，不引入任何外部资源。
竞品佐证：Renode VSD 3D 渲染为桌面端引擎产物、非浏览器交互式产品树【已查证·来源#B32,B33】；Web 端「3D 原型构建 + 调试联动」组合无竞品提供（见 2.5）。
CHAPTER 6

MVP 范围与验收标准

范围（六层映射）→ 端到端验收场景 → 可测验收标准清单 → 延迟项

结论先行：MVP = 轻量 RISC-V ISS(RV32IMC) + UART/GPIO/定时器 + 内存映射 + 2D/树形多层原型 + 单步/断点 + 内存查看 + 反汇编·源码联动 + 简易波形 + 多视图 Web 前端（WebSocket + WASM），以「智能灯」固件端到端走通为验收主线。 MVP 与六层模型逐层映射，13 条 P0 功能需求（FR-01~FR-12 + FR-23）即 MVP 交付集；性能目标全部标注【估算】，实现后以真实测量校准。可交互 3D 模型视图（FR-21）、屏幕 GUI 帧缓冲渲染（FR-22）与多板互联（FR-24~27，v1.2 评审补充）明确不进 MVP 验收项，列入 P1 里程碑（见 6.4）。多板互联不在 MVP 验收项内，列入 P1——理由：跨板时钟/事件同步与消息路由复杂度较高，MVP 应聚焦单板「搭建→加载→运行→观察→单步→判定」闭环稳妥落地；多板互联作为可配置能力预留接口，MVP 架构（L3 事件队列/消息路由抽象、L1 外设「端口-链路」解耦）不阻塞后续扩展。MVP 多层原型用轻量方案快速闭环：2D 原理图 / 结构化产品树（文本/树形，可点选下钻）。

6.1 MVP 范围（六层模型映射）

层MVP 交付说明
L0 产品/系统层产品树根节点 + 场景绑定（简化命名）产品/场景为树根与行为判定的锚点（FR-01）

6.2 端到端验收场景（E2E-01 · 智能灯 demo）

剧本：验证「产品行为判定」闭环——LED 闪烁 + 按键计数 + UART 打印的固件在浏览器内跑通并完成调试观察。

  1. 搭建（L0/L1）：新建产品「智能灯」→ 添加主板「Demo Board」→ 挂载 MCU(RV32IMC)、GPIO-LED、GPIO-KEY、定时器、UART；内存映射自动生成（FR-01/02/03）。
  2. 加载（L5）：上传 demo 固件 ELF（UART 周期打印 tick、定时器翻转 LED、按键计数）→ 调试视图反汇编区正确显示（含 DWARF 时与源码区对应），入口 PC 正确（FR-05/23）。
  3. 运行（L3）：点击运行 → 串口终端出现周期打印、虚拟时间推进（FR-06/07/11）。
  4. 观察波形（L4）：暂停 → 切换至波形视图（独立路由）可见 TIMER_CMP 翻转与 GPIO0 电平变化（FR-10/23）。
  5. 单步（L4）：单步 3 条指令 → PC/寄存器逐条变化、反汇编当前行与源码行（含 DWARF 时）同步高亮（FR-08/05）。
  6. 查内存（L4）：watch tick_cnt 递增、led_on 翻转（FR-09）。
  7. 判定（双闭环）：修改固件（如改变闪烁周期）→ 重跑 → 波形周期变化 → 产品行为判定通过（FR-12 确定性）。

6.4 延迟项（P1/P2，不进 MVP）与 P1 里程碑建议

  • 可交互 3D 原型视图（FR-21，P1）：three.js 引擎，产品外壳→主板→元器件 旋转/缩放/点选下钻。
  • 屏幕 GUI 帧缓冲渲染（FR-22，P1）：LCD framebuffer 外设模型 + 帧缓冲更新时序 + 3D 屏幕纹理映射（LVGL 等 GUI 实时渲染）。

  • 跨板调试联动（FR-26，P1）：多板内存/寄存器/反汇编并排 + 跨板信号/消息跟踪。
  • 跨板波形同步（FR-27，P1）：多板波形按同一虚拟时间轴对齐；跨板链路信号纳入探针采样。
  • 反向调试/状态快照（FR-19，借鉴 Simics 检查点）
  • 指令覆盖率与访存 trace 分析（FR-14）
  • GDB RSP 对外兼容（FR-15，借鉴 Synopsys/Proteus 路径）
  • 脚本化/CI 接口（FR-16，借鉴 Renode Robot Framework【已查证·来源#B9】）
  • 多核/SMP 扩展（FR-18）
  • 产品行为脚本/场景断言（FR-17）与协作分享（FR-13 服务端版）
  • 性能监控面板（FR-20）

P1 里程碑建议（评审点 2 + 用户决定 + v1.2 评审补充）：里程碑 A（3D 与屏幕 GUI 渲染）——MVP 闭环（2D/树形多层原型 + 调试联动）→ 2D/树形增强（原理图、布局编辑）→ 3D 模型与点选下钻（FR-21）→ 屏幕帧缓冲渲染到 3D 表面（FR-22）；理由：3D 与屏幕 GUI 渲染依赖仿真内核的帧缓冲更新时序与外设模型（L1/L3），先以 2D/树形验证闭环价值、再叠加 3D 交互与 GUI 渲染，可控制集成复杂度与性能风险。里程碑 B（多板互联）——单板闭环（MVP 交付态）→ 多板拓扑与板间外设互联（FR-24/25）→ 跨板联合调试与波形同步（FR-26/27）；理由：跨板时钟/事件同步与消息路由复杂度较高，须先让单板「搭建→加载→运行→观察→单步→判定」闭环稳妥落地，再扩展多板；可调说明：多板互联作为可配置能力预留接口（L3 事件队列/消息路由抽象、L1 外设「端口-链路」解耦），MVP 架构不阻塞后续扩展，跨板同步复杂度列风险 R10。
